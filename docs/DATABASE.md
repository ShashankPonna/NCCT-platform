## Core Entities

**profiles** — one row per user (Admin, Trainer, Trainee, Employer), linked 1:1 to a Supabase Auth user. Holds role, name, contact, and role-specific fields (trainee: cooperative/PACS affiliation; employer: org name/sector). `public_profile_code` (nullable, unique) and `nfc_tag_uid` (nullable, unique) are F10's two independent NFC-card lookup keys — see [DECISIONS.md](DECISIONS.md) #30 for why they're separate columns rather than one, and why the code is rotatable while the UID is a card's fixed factory identifier.

**institutions** — VAMNICOM/RICM/ICM records; programmes belong to an institution.

**programmes** — a training programme: title, dates, mode, capacity, target audience, owning institution.

**nominations** — join entity between `profiles` (trainee) and `programmes`, with approval status (pending/approved/waitlisted) and enrollment date.

**notifications** — in-app notification rows ([DECISIONS.md](DECISIONS.md) #65, migration `20260925000002`), one per recipient per event. `type` is one of a fixed CHECK-constrained set (`nomination_decided`, `nomination_submitted`, `lesson_published`, `assessment_available`, `session_scheduled`, `certificate_issued`, `hostel_assigned`, `job_shortlisted`, `job_interest_updated`, `trainer_assigned` — mirrored by `NOTIFICATION_TYPES` in `packages/constants`). `data` (jsonb) holds the event's parameters, **not** rendered text: the client builds the message per locale from `type` + `data`, so one row reads correctly in English or Hindi. `read_at` null = unread. Written only by Express via `supabaseAdmin` (`apps/api/src/notificationService.ts`, best-effort fan-out after the triggering write succeeds); read via `req.supabase` under own-row RLS; marked read via `supabaseAdmin` always filtered by `req.user.id`. Indexed on `(recipient_id, created_at desc)`.

**hostels / hostel_rooms / trainee_hostel_assignments** — minimal, record-keeping-only hostel reference data ([DECISIONS.md](DECISIONS.md) #64, migration `20260925000001`). A `hostels` row belongs to an institution; `hostel_rooms` belong to a hostel (`room_number` unique per hostel, `type` is `dorm`/`shared`/`single` as a text CHECK, `capacity` is informational only — nothing enforces it). `trainee_hostel_assignments` records which room a trainee has for a given programme: `unique (trainee_id, programme_id)`, so re-assigning replaces the row (upsert), and any number of trainees can share a room — no availability, booking, or check-in/out logic exists by design. `room_id` has **no** cascade, so deleting a room or hostel that still has trainees assigned fails on the FK (the API returns 409) rather than silently erasing where trainees were recorded as staying. The table has two FKs into `profiles` (`trainee_id`, `assigned_by`), so any `profiles` embed on it needs the `profiles!trainee_id` hint (see #62). Written only by admin-only Express routes via `supabaseAdmin` (`hostels.ts`, and inline on nomination approval in `nominations.ts`); a room must belong to a hostel of the programme's own institution. Surfaced to trainees on their private profile only — never on the public NFC profile, which needs no login.

**programme_trainers** — join entity between `profiles` (trainer) and `programmes` ([DECISIONS.md](DECISIONS.md) #52, migration `20260924000001`), admin-assigned: which trainer(s) can manage a given programme's courses/modules/lessons/content-translations/assessments/course-skills and its timetable sessions/attendance. `primary key (programme_id, trainer_id)` — many-to-many, a programme can have several trainers and a trainer several programmes. Written only by the admin-only `POST`/`DELETE /programmes/:id/trainers` routes via `supabaseAdmin`; read by every other admin/trainer content and attendance route in `apps/api/src/programmeAccess.ts`'s `requireProgrammeAccess` middleware, which walks each resource (course/module/lesson/assessment/assessment_question/timetable_session) up to its programme id and checks the caller (if a trainer, not an admin) has a row here for it.

**timetable_sessions** — sessions within a programme (date/time/location), used by both the timetable view and attendance. Also carries `check_in_code`, a unique 6-digit numeric code generated server-side at creation ([DECISIONS.md](DECISIONS.md) #38) — a short, spoken/written-friendly alias for the session's UUID, resolved back to it via `GET /api/timetable-sessions/code/:code`. QR check-in is unaffected; the code exists only for the two places a human previously had to handle the raw UUID by hand (faculty pulling up a session in `AttendanceManager.tsx`, and a trainee's manual check-in fallback).

**courses / modules / lessons** — LMS content hierarchy. A `programme` may map to one or more `courses`; a `course` has `modules`; a `module` has `lessons`. A lesson's `content_type` is one of `video | pdf | slides | text | interactive`. PDF/slides content uses `storage_path` against the `lesson-content` Supabase Storage bucket (see Storage section below). Video content (SIH prototype) uses `video_id` instead — the 11-character ID of a YouTube **unlisted** video, `CHECK`-constrained to that exact format so a full URL can never be stored by mistake; see [DECISIONS.md](DECISIONS.md) #12 for why and how this swaps out later. Interactive content uses `interactive_config` (jsonb) — currently one exercise type, `matching`; see [DECISIONS.md](DECISIONS.md) #14 for why this is jsonb rather than normalized tables. A lesson only ever uses the field(s) matching its `content_type` — nothing enforces that exclusivity at the DB level yet (`TBD` if it should).

**content_translations** — per-lesson translation rows keyed by lesson ID + locale (e.g. `en`, `hi`), supporting the MVP's multi-language requirement. The _primary_-language content also lives here as a normal locale row, not inline on `lessons` — a lesson's base row only ever carries structural fields (`title` as a fallback label, `content_type`, media pointers), not the actual body text. The locale itself is validated by shape only (`^[a-z]{2}(-[A-Z]{2})?$`) — PRD §14 hasn't settled which second language ships, so the API deliberately doesn't hardcode a locale enum; `packages/constants`' `SUGGESTED_LOCALES` is only a UI convenience list, not a DB-level constraint.

**lesson_progress** — per-trainee, per-lesson progress (%, last position, completed_at). Written by both web and mobile through the same Express endpoint; this is also the table the offline-sync queue replays into.

**assessments / assessment_questions** — quiz definitions tied to a module. `assessment_questions.correct_option_id` must never reach a trainee taking the quiz — this table has no RLS read policy at all (unlike every other content table), and every read goes through Express (`supabaseAdmin`), which strips that field before responding to a trainee. See [DECISIONS.md](DECISIONS.md) #15. `assessments.kind` ([DECISIONS.md](DECISIONS.md) #53, migration `20260924000002`) is `'quiz'` (practice, ungraded, never gates a certificate, reveals answers after every attempt) or `'module_test'` (graded, counts toward a course's marks tally, must be passed for the certificate) — default `'module_test'` so every pre-existing assessment keeps its prior certificate-gating behavior. `.max_attempts` (nullable = unlimited) is enforced server-side in `assessmentAttempts.ts`, never client-side only. `assessment_questions.marks` (default 1) weights a question's contribution to the assessment's total — grading sums marks for correct answers, not a flat question count.

**assessment_attempts** — a trainee's submitted answers + server-computed score (`score_percent`/`passed` are always computed in Express from `assessment_questions.correct_option_id`, never trusted from the client, per CLAUDE.md's security rules — verified live: a request body claiming `score_percent: 100, passed: true` alongside all-wrong answers is silently ignored and graded correctly as 0%/failed). `.marks_obtained`/`.total_marks` ([DECISIONS.md](DECISIONS.md) #53) are snapshots of the marks-weighted grading at submission time — a later edit to a question's marks never retroactively changes a past attempt's recorded result. Existing rows were backfilled from `score_percent` × their assessment's question count at migration time (an approximation if questions were added/removed since).

**certificates** — issued on **course completion**: every lesson across every module of a course marked complete, and every module assessment in that course (if any) passed. This resolves what used to be an open question here — every passing assessment minting its own certificate — per direct user request; see [DECISIONS.md](DECISIONS.md) #37. One row per `(trainee_id, course_id)` (`certificates_trainee_course_unique`), checked idempotently from two trigger points: a lesson being marked complete (`lessonProgress.ts`) or an assessment being passed (`assessmentAttempts.ts`) — either can be the *last* thing needed to finish a course, and the check is a no-op if the course isn't fully done or is already certified. Columns: unique `certificate_code` (format `NCCT-XXXXXXXX`, an 8-char code from a 32-character alphabet that excludes visually-ambiguous characters — `0/O/1/I` — to avoid transcription errors when read off a printed certificate), a QR code (embedded in the generated PDF, encoding a link to the public verification page) plus the row itself, PDF file reference (Storage), issuing institution, issue date. `course_id` (not null) is the certifying unit; `assessment_attempt_id` is now **nullable** — set to the most recent passing attempt for audit purposes when the course has assessments, `null` for a pure lesson-only course with nothing to point at. Public verification reads from this table only (`certificates_public_read` RLS policy, already public at the DB layer — Express's `GET /api/certificates/:code` just adds a lookup-by-human-code and denormalizes trainee/course/programme/institution names for display), with no other data exposed. `course_id`/`programme_id`/`issuing_institution_id` are derived server-side, not supplied by the caller. `.marks_obtained`/`.total_marks`/`.score_percent` ([DECISIONS.md](DECISIONS.md) #53) are the sum of the trainee's best attempt on every `module_test` assessment in the course, computed once at issue time and frozen thereafter (a later attempt on an already-certified course doesn't retroactively change the certificate) — `null` for a course with no module tests. Practice-quiz (`kind = 'quiz'`) attempts are never included, whatever their score.

**attendance_records** — per-trainee, per-session attendance, with a `method` field (`qr` | `face` | `manual`) and, for face matches, the similarity score that triggered the match. `manual` (migration `20260901000018`, [DECISIONS.md](DECISIONS.md) #47) is a trainer/admin directly ticking a trainee present from the class roster, like a real college ERP's attendance register — the row's `marked_by` column (nullable, `references profiles(id)`) records who, since a manual mark has no independent verification signal of its own the way a QR scan or face-match score does. `unique (session_id, trainee_id)` (from the initial migration) means presence is existence: a row means present, no row means absent/unmarked — the manual-mark routes work within that same shape rather than adding a boolean.

**face_embeddings** — one (or more, for re-enrollment) embedding per trainee, stored as a `vector(1024)` (pgvector) column — originally `vector(512)` on the mistaken assumption that Human and InsightFace `buffalo_l` share an output size; they don't (Human is 1024-d, buffalo_l 512-d), corrected in migration `20260901000011` after measuring the real model output, plus `consent_given_at` (required before any row is written — see CLAUDE.md security rules) and which model produced it (`human` | `insightface_buffalo_l`) so a future model swap doesn't silently mix incompatible embeddings.

**jobs** — employer-posted openings: title, required skills, location, owning employer. Own-row RLS write (`jobs_insert_own`/`_update_own`/`_delete_own`, F6); reads are public (`jobs_public_read`, from the initial migration) — Express's `GET /api/jobs`/`GET /api/jobs/:id` have no `requireAuth` at all, matching that RLS design. `embedding vector(384)` (nullable) was added for P3 AI Job Matching ([DECISIONS.md](DECISIONS.md) #28) — best-effort, computed from title/description/required_skills plus any P1 taxonomy-tagged skills, never blocking the write itself. `match_jobs(query_embedding, match_count)` is the ranking RPC (same "PostgREST can't express `<=>`, so a SQL function does it, EXECUTE granted only to `service_role`" pattern as `match_corpus_chunks`), never called directly by a client.

**job_interests** — employer shortlist / trainee-interest join entity between `profiles` (trainee) and `jobs`, with a `status` (`shortlisted`/`viewed`/`contacted`). Trainees can read their own rows (`job_interests_select_own`, F6); the employer side deliberately has no RLS policy at all — "does this employer own the job this interest points at" is a cross-table check, enforced in Express (fetch the job via `supabaseAdmin`, compare `employer_id`) rather than an RLS EXISTS-subquery, same reasoning as `assessment_questions`' Express-only gating (DECISIONS.md #15) though for a different underlying reason (cross-table ownership, not column-hiding).

**visibility_settings** — trainee's opt-in/opt-out flag for appearing in employer search (referenced by PRD edge cases around what happens to existing shortlists on opt-out — behavior `TBD`, and still not resolved by F6: opting out does not retroactively remove existing `job_interests` rows, the simplest default given no cleanup was built, not a considered design choice). Already had full own-row RLS (`visibility_settings_own`, `for all`) from the initial migration. `public_profile_enabled` (F10, added `20260901000014`) is a deliberately separate consent flag from `visible_to_employers`, not a reuse of it — it gates an unauthenticated public URL, a different audience than the employer portal behind a login. See [DECISIONS.md](DECISIONS.md) #30.

**chatbot_corpus_chunks** — embedded chunks (pgvector) of programme/FAQ content used for RAG retrieval by the chatbot service. `embedding` is `vector(384)` — `Xenova/all-MiniLM-L6-v2`, generated locally in Express (see [DECISIONS.md](DECISIONS.md) #17); it was `vector(1536)` as a placeholder until F7 chose the provider. Has an HNSW cosine index and **no RLS policy at all**, deliberately: no client reads the corpus directly, since `POST /api/chatbot/ask` returns only the answer plus the specific snippets it grounded that answer in. Similarity search goes through `match_corpus_chunks(query_embedding, match_count)`, a SQL function — PostgREST's query builder can't express pgvector's `<=>` operator — whose EXECUTE grant is revoked from `public`/`anon`/`authenticated` and granted only to `service_role`, matching how `20260901000002` hardened `handle_new_user` off the RPC surface.

**skills** — the shared skill taxonomy P1 Skill-Gap Analysis introduced ([DECISIONS.md](DECISIONS.md) #26), admin-curated (name, optional category). Previously the schema had no first-class skills concept at all — only `jobs.required_skills text[]`, free text with nothing to match against.

**job_skills** — join entity tagging a job posting against the `skills` taxonomy (distinct from, and additive to, `jobs.required_skills`' free text). Public read, matching `jobs_public_read`. No RLS write policy: "does this employer own the job" is a cross-table check, enforced in Express the same way `job_interests`' employer-write side already is.

**programme_skills** — join entity: skills a trainee is read as having _acquired_ by earning a certificate under this programme. This is the acquisition source `skillGapService.ts`'s `getSkillGap` reads (via `certificates.programme_id`, already a direct column — no join through assessments/modules/courses needed). Authenticated read, matching `programmes_read_authenticated`. Admin/trainer write via `supabaseAdmin`, same content-authoring pattern as `courses`/`modules`/`lessons`.

**course_skills** — finer-grained sibling of `programme_skills` ([DECISIONS.md](DECISIONS.md) #45, migration `20260901000017`): skills a trainee acquires via the specific *course* their certificate certifies (`certificates.course_id`), not the whole programme. `getAcquiredSkills` unions both tables — a trainee gets everything tagged on the whole programme plus everything tagged on their specific certified course, so a programme still tagged only at the broad level keeps working unchanged. Same RLS shape as `programme_skills` (`course_skills_read_authenticated`, admin/trainer write via `supabaseAdmin`). **Handled defensively in code**: since every certificate has carried a non-null `course_id` since #37, any query against this table on a project that hasn't yet applied the migration would otherwise break the already-shipped programme-level gap check — `skillGapService.isMissingCourseSkillsTable()` specifically catches PostgREST's "table not in schema cache" error (`PGRST205`) and degrades to "no course-level skills yet" rather than propagating it, so pre-migration behavior stays byte-for-byte identical to before #45.

**sync_queue** _(client-local concept, not a server table)_ — the mobile app's local queue of pending writes while offline; it is not part of the server schema, listed here only so the relationship between offline mobile storage and the server tables above is clear (each queued item ultimately targets one of `lesson_progress`, `assessment_attempts`, or `attendance_records`).

## Row Level Security

RLS is enabled on every table. Only tables with an already-decided access rule have a real policy so far:

- Self-access: `profiles`, `lesson_progress`, `assessment_attempts`, `visibility_settings`.
- Own-row select only: `notifications` (`notifications_select_own`, added for [DECISIONS.md](DECISIONS.md) #65) — every role reads only their own rows. No insert/update policy: fan-out inserts and read-marking go through Express via the service-role client, the latter always filtered by `req.user.id`.
- Own-row select only: `trainee_hostel_assignments` (`trainee_hostel_assignments_read_own`, added for [DECISIONS.md](DECISIONS.md) #64) — a trainee can see their own room assignments; all writes go through the admin-only Express routes via the service-role client. `hostels`/`hostel_rooms` get **no** policy (default-deny, same as `institutions`) — every read and write goes through admin-only Express routes.
- Own-row select only: `programme_trainers` (`programme_trainers_read_own`, added for [DECISIONS.md](DECISIONS.md) #52) — a trainer can see which programmes they're assigned to; all writes (assign/unassign) go through the admin-only Express routes using the service-role client, same pattern as `nominations`' decision route.
- Own-row select + insert: `attendance_records` (`attendance_records_own` from the initial migration was select-only; `attendance_records_insert_own` added for F5 — a trainee's own check-in, either method, goes through `req.supabase`, not `supabaseAdmin`). `face_embeddings` (`face_embeddings_select_own`/`_insert_own`, both added for F5 — same reasoning). Cross-trainee reads (an admin/trainer's session roster) still go through `supabaseAdmin` in Express.
- Own-row full CRUD (select/insert/update/delete): `jobs` (`jobs_insert_own`/`_update_own`/`_delete_own`, F6 — plus the pre-existing public-read policy below); `visibility_settings` (`visibility_settings_own`, `for all`, from the initial migration).
- Own-row select only: `job_interests` (`job_interests_select_own`, F6 — a trainee sees their own shortlist entries; the employer-write side has no policy at all, see the `job_interests` entity note above).
- Public read: `certificates`, `jobs` (PRD §6.4/§6.6). `job_skills` (`job_skills_public_read`) — a job's tagged skills, same "public job-board data" level as `jobs_public_read`; added for P1 (DECISIONS.md #26).
- Authenticated read: `programmes` (`programmes_read_authenticated`), `timetable_sessions` (`timetable_sessions_read_authenticated`) — any logged-in user can browse the catalog/timetable; added for F2. `courses`/`modules`/`lessons`/`content_translations` (`courses_read_authenticated`/`modules_read_authenticated`/`lessons_read_authenticated`/`content_translations_read_authenticated`) — any logged-in user can browse LMS content in any language it has a translation for; added for F3. `assessments` (`assessments_read_authenticated`) — any logged-in user can see what assessments exist for a module; added for F4. `skills`/`programme_skills` (`skills_read_authenticated`/`programme_skills_read_authenticated`) — the taxonomy and what a programme grants; added for P1. Writes to all of these go through the admin/trainer-only Express routes using the service-role client, same pattern as `nominations`.
- **No policy, deliberately** (not the same as "not built yet"): `assessment_questions` gets no read policy at all, ever, by design — see [DECISIONS.md](DECISIONS.md) #15. Every read goes through Express. `job_interests`' employer-write side is a related but distinct case (see above): not a column-hiding problem, a cross-table ownership check RLS can't express as a simple row predicate. `chatbot_corpus_chunks` is a third case, and the simplest: no client has any reason to read the corpus directly (F7's ask route returns only the answer and its cited snippets), so it stays default-deny — and its `match_corpus_chunks` RPC is likewise granted only to `service_role`, keeping retrieval an Express-side concern.
- Own-row insert/select: `nominations` (`nominations_insert_own`/`nominations_select_own` — a trainee can create and see their own nomination but not edit/decide it; status changes go through the admin-only Express route using the service-role client, per DECISIONS.md #9's explicit example).
- F10's public-profile and kiosk lookups get **no new RLS policy at all** — `profiles` stays self-access-only, matching how `certificates.ts`'s public verification route already works (DECISIONS.md #30): both new reads go through `supabaseAdmin` in Express, which is the deliberate boundary, not a gap to fill in later.

Every other table is enabled but has no policy yet — default-deny — and gets one added alongside the feature route that needs it, not invented speculatively here. See [DECISIONS.md](DECISIONS.md) #9 for why RLS is a real second layer rather than theoretical, given Express's service-role/per-user client split.

## Storage

Two buckets, both provisioned directly via the Storage Management API (`POST /storage/v1/bucket`), not a SQL migration — Storage buckets aren't plain Postgres rows in the portable-migration sense, so there's no `supabase/migrations/*.sql` file for either; if a bucket ever needs to be recreated (e.g. a fresh project), redo it with the same API call rather than trying to derive it from a migration file. Neither bucket needs `storage.objects` RLS policies because every read/write to both goes through `supabaseAdmin` (service-role, bypasses Storage RLS same as it bypasses table RLS).

- `lesson-content` — **private** (`public: false`), 25 MB file size limit, MIME types restricted to `application/pdf`, `.pptx`, `.ppt`. See [DECISIONS.md](DECISIONS.md) #13 for the upload/read-via-signed-URL pattern. Object paths follow `{lesson_id}/{timestamp}-{original_filename}`.
- `certificates` — **public** (`public: true`), 5 MB file size limit, `application/pdf` only. Public is intentional here, not an oversight: the `certificates` table already has a fully public `certificates_public_read` RLS policy (PRD §6.4's "no-login verification"), so a certificate's own PDF file being equally public is consistent, not a bigger exposure than the DB row already is. Object paths are just `{certificate_code}.pdf`.

## Open Items

- Whether `certificates` needs a revocation/status field (PRD Open Question) — deliberately not in the initial migration.
- Whether `job_interests` rows persist after a trainee opts out via `visibility_settings` (PRD Open Question).
- Retention policy for `face_embeddings` if a trainee withdraws consent — not yet designed.
- ~~`chatbot_corpus_chunks.embedding` is `vector(1536)` as a placeholder~~ — **resolved in F7**: now `vector(384)` for the locally-run `Xenova/all-MiniLM-L6-v2` model ([DECISIONS.md](DECISIONS.md) #17, which also documents what a later swap to a hosted provider would cost).
- `CHATBOT_RETRIEVAL_COUNT` (5) and `CHATBOT_MIN_SIMILARITY` (0.25) in `packages/constants` are starting points tuned against a 3-chunk test corpus, not measured optima — the same category of judgment call as `FACE_MATCH_THRESHOLD`. The similarity floor is the one that matters: without it, an off-topic question still retrieves the "nearest" chunks and the model would be handed irrelevant material to ground an answer in. Worth re-tuning once a real corpus exists.
- Corpus chunking is caller-supplied: `POST /api/chatbot/corpus` embeds exactly the text it's given (max 4000 chars), with no automatic splitting of long documents into overlapping windows. Fine for hand-authored FAQ/programme blurbs, which is what the MVP needs; a real document-ingestion pipeline would need a chunking strategy.
- Jobs posted before `20260901000013_p3_job_matching.sql` have `embedding = null` and won't appear in a trainee's ranked matches until a later write (any `PATCH` or a skill re-tag) recomputes it. No backfill script exists — at this project's data volume, a no-op `PATCH` per job is a one-line fix; worth a real backfill pass if the job count ever grows past hand-fixing.
- `DROPOUT_RISK_*` thresholds in `packages/constants` (P6, [DECISIONS.md](DECISIONS.md) #29) are hand-tuned starting points, not measured optima — same category of judgment call as `FACE_MATCH_THRESHOLD`/`CHATBOT_MIN_SIMILARITY`. There's no historical dropout data in this project yet to tune or validate against.
- `lessons` has no DB-level constraint forcing `storage_path`/`video_id` exclusivity by `content_type` (e.g. a `video` row could technically also have `storage_path` set) — left unenforced for now since the Express validation schemas already keep them separate per-request; revisit if lessons end up written from more than one path.
- Course/module/lesson write access (`courses`/`modules`/`lessons` admin routes) is `admin` or `trainer` — a judgment call made when F3 was built, not an explicit PRD statement; revisit if PRD is clarified on who authors content. **Since [DECISIONS.md](DECISIONS.md) #52**, a trainer additionally has to be assigned to the specific programme via `programme_trainers` — this was a real gap until then (any trainer could edit any programme's content or mark any session's attendance, not just their own).
- Re-uploading a lesson's PDF/slides content overwrites `lessons.storage_path` but doesn't delete the previous Storage object — an accumulating orphan, not a correctness bug (the old file is just unreferenced, never served again). Worth a cleanup pass (delete-on-overwrite, or a periodic sweep) before this goes past prototype.
- Every passing `assessment_attempts` row currently mints its own certificate — there's no "this is the programme's capstone assessment" concept anywhere in the schema, so a trainee passing multiple per-module quizzes in one programme gets multiple certificates. This is the literal reading of PRD §6.4 ("on pass"), not a bug, but worth confirming against actual intent.
- Assessment/question write access (`admin`+`trainer`) follows the same judgment call as course/module/lesson write access above, for the same "PRD doesn't say" reason.
- Face check-in matches 1:1 (a logged-in trainee's submitted embedding against only _their own_ enrolled `face_embeddings` row(s)), not 1:N (searching all trainees to identify an unknown face) — a judgment call, since PRD doesn't specify either way; 1:1 is simpler, cheaper, and consistent with the trainee already being authenticated via JWT before submitting a check-in. Revisit if a genuine "identify an unclaimed face" use case shows up.
- `FACE_MATCH_THRESHOLD` (`packages/constants`, currently `0.6`) is an unvalidated starting point, not a tuned value — same category of open judgment call as F4's `pass_threshold_percent` was. Worth revisiting once there's real enrollment/check-in data.
- Face embedding _extraction_ happens in the browser (`apps/web`), not Express — see [DECISIONS.md](DECISIONS.md) #16. This doesn't change anything about this table's shape or RLS, only where the 1024-number `embedding` array passed to `POST /api/face-embeddings` was computed.
- ~~No dedicated "skills" taxonomy exists anywhere in the schema~~ — **resolved by P1** (DECISIONS.md #26): `skills`/`job_skills`/`programme_skills` now exist. ~~F6's employer search still does its own keyword match, not unified with the taxonomy~~ — **resolved** (DECISIONS.md #45): `GET /employer/trainees` now also accepts an exact `?skill_id=` filter and matches free-text `q` against a trainee's real acquired skill names, alongside (not instead of) the original programme/institution-title match, since not every certified programme is taxonomy-tagged.
- F6's shortlist flow (`POST /api/jobs/:jobId/interests`) additionally requires the target trainee to currently have `visibility_settings.visible_to_employers = true`, not just excludes invisible trainees from search results — a judgment call extending PRD §6.6's visibility control to the whole employer-facing surface (an opted-out trainee can't be shortlisted by a direct `trainee_id` either), not only literally "must not appear in new searches." Not explicitly required by PRD, but the more conservative reading of trainee consent.
- Opting out of `visibility_settings` does not remove or otherwise affect existing `job_interests` rows — PRD §11's open question ("existing shortlist entries `TBD` whether they persist") is left at its simplest default (they persist) because no cleanup was built, not because persistence was judged correct.
