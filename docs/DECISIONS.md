# Architecture Decisions

Lightweight decision log — why key choices were made, so future changes are deliberate reversals rather than silent drift. Add a new entry (don't edit past ones) when a decision changes; mark the old one Superseded.

---

### 1. One backend serves both web and mobile

**Decision**: Single Node/Express REST API consumed by both the React web app and the React Native app; no separate mobile-specific API.
**Why**: A REST API doesn't need to know whether its caller is a browser or a phone. Duplicating it would double the bug surface and let web/mobile drift out of sync on business logic.
**Status**: Active.

### 2. One shared Supabase database

**Decision**: Single Supabase Postgres instance for both clients, accessed only through Express.
**Why**: Follows directly from Decision 1 — a shared backend implies a shared data source. No product reason for web-only or mobile-only data.
**Status**: Active.

### 3. Separate UI codebases (React web + React Native), not React Native Web

**Decision**: Web and mobile have independent UI code; only the logic layer (`packages/*`) is shared.
**Why**: The two surfaces have genuinely different UI shapes — dashboard/table-heavy admin+employer screens on web vs. camera/NFC/offline-native trainee screens on mobile. Forcing one UI codebase via RN-Web would fight both use cases.
**Status**: Superseded by #19 — the "camera/NFC-native trainee screens" premise turned out to be wrong (see #19); the React-Native-vs-web split doesn't apply once mobile no longer needs native camera/NFC.

### 4. Clients never call Supabase directly

**Decision**: All data access goes through Express; Supabase service credentials are server-side only.
**Why**: Centralizes auth checks, face-recognition matching, PDF generation, and chatbot orchestration in one place instead of duplicating business rules in RLS policies and two clients.
**Status**: Active.

### 5. Face recognition: `@vladmandic/human` as default, InsightFace `buffalo_l` as swap-in alternative

**Decision**: Use the JS-native `@vladmandic/human` library (runs in Node via tfjs-node) for face detection/embedding extraction in the Express face-rec service. If accuracy proves insufficient, swap the extraction step to InsightFace's `buffalo_l` ONNX models (mirrored on Hugging Face) via `onnxruntime-node` — the storage/comparison logic downstream (pgvector cosine similarity) stays the same either way.
**Why**: Human integrates fastest given an all-JS/TS stack and runs on both Node and React Native. `buffalo_l` is higher accuracy but adds ONNX-inference wiring; kept as a documented fallback rather than the default to avoid premature complexity.
**Status**: Amended by #16 — the library choice (`@vladmandic/human`) is still active, but _where extraction runs_ changed from "the Express service" to "the browser client." **Dimension correction**: the two options in this decision do **not** produce the same descriptor size, contrary to what the initial schema assumed — Human's faceres output is **1024-d**, InsightFace `buffalo_l` is 512-d (measured, not assumed; see migration `20260901000011`). Swapping to `buffalo_l` later therefore means recreating `face_embeddings.embedding` at 512 and re-enrolling every trainee, not just changing the extraction call. Revisit after real-world accuracy testing.

### 6. NFC: static NDEF URI tag, not custom in-app read/write

**Decision**: NFC cards encode a URL to the trainee's public profile page (reusing the certificate-verification page pattern), written once at issuance. No custom NFC read/write logic is built into the apps for MVP.
**Why**: NFC tags hold too little storage (144–888 bytes on common tags) for a full profile — a URL is the only sane payload. Tapping a tag with a native OS NFC reader opens the URL on both Android and iOS with no app installed, sidestepping Web NFC's Chrome-Android-only support and iOS's tag-write restrictions.
**Status**: Active.

### 7. Offline sync: timestamp/last-write-wins, not CRDT/OT

**Decision**: Mobile queues offline writes locally and replays them against the same Express endpoints on reconnect; conflicts resolved by last-write-wins on client timestamp.
**Why**: The data involved (progress events, quiz results, attendance) is mostly append-only, not collaboratively edited — a full CRDT/operational-transform sync engine would be solving a problem this data shape doesn't have.
**Status**: Active. Fairness edge cases near deadlines are a known open question (see PRD §14).

### 8. Monorepo: pnpm workspaces, not Turborepo/Nx

**Decision**: Use plain pnpm workspaces to let `apps/*` import from `packages/*` locally.
**Why**: Sufficient for the project's current size; Turborepo/Nx's build-caching benefits aren't needed until build times or team size actually justify the extra tooling.
**Status**: Active. Revisit if build/CI times become a real pain point.

### 9. Express uses per-user Supabase clients for user-owned data, service-role only for privileged operations

**Decision**: The auth middleware builds a request-scoped Supabase client using the caller's own JWT (so Postgres RLS evaluates as that user) for routes acting on a user's own data. A separate service-role client (`supabaseAdmin`) is used only where the operation is legitimately cross-user or privileged (e.g., admin approving a nomination, issuing a certificate, writing a face embedding after consent).
**Why**: `CLAUDE.md`'s security rule states Express role middleware and Supabase RLS are "defense in depth, not either/or." That's only true if Express doesn't call Supabase exclusively with the all-powerful service-role key (which bypasses RLS entirely) — otherwise RLS is enabled but inert. Splitting the client this way makes RLS a real second layer instead of a checkbox.
**Status**: Active. Individual routes still decide per-case which client to use; there's no automatic rule beyond "user's own data → user-scoped client."

### 10. Vitest (not Jest) for `apps/api` tests

**Decision**: Use Vitest + Supertest for API tests instead of the originally proposed Jest + Supertest.
**Why**: `apps/api` is ESM (`"type": "module"`) with `NodeNext` module resolution. Jest's ESM support requires extra transform/config friction (`ts-jest` ESM preset, `extensionsToTreatAsEsm`, moduleNameMapper for `.js` specifiers) that Vitest avoids natively — it was faster to get a real, working test running than to fight Jest's ESM setup. `CLAUDE.md`'s testing section explicitly said "confirm before first test is written, then remove the caveat"; this is that confirmation.
**Status**: Active for `apps/api`. Web is a natural fit for Vitest too (same Vite tooling) if/when its test setup is confirmed. Mobile stays Jest (`jest-expo` preset) since that's the RN/Expo ecosystem standard, not Vitest.

### 11. `apps/api` splits `app.ts` (Express app, exported) from `index.ts` (thin `listen()` entrypoint)

**Decision**: `apps/api/src/app.ts` builds and exports the configured Express app; `apps/api/src/index.ts` only imports it and calls `.listen()`.
**Why**: Supertest needs an importable `app` object to test against directly, without binding a real port. This is the standard pattern for testable Express apps, not a speculative abstraction — it was introduced exactly when the first test needed it, per `CLAUDE.md`'s "minimal change that satisfies the requirement."
**Status**: Active. Every future route file goes in `apps/api/src/routes/` and is mounted onto `app` in `app.ts`.

### 12. Lesson video hosted as YouTube unlisted videos (prototype), PDFs stay on Supabase Storage

**Decision**: For the SIH prototype, `lessons.content_type = 'video'` rows store only an 11-character `video_id` (validated by regex both client-side via zod and DB-side via a `CHECK` constraint) — never a full URL, never the video file itself. The web app embeds it with the official `https://www.youtube.com/embed/{video_id}` iframe player via a reusable `YouTubeVideoPlayer` component (`apps/web/src/YouTubeVideoPlayer.tsx`). Non-video lesson content (PDF/slides) continues to use `lessons.storage_path` against Supabase Storage, as already implied by the initial schema — this decision only concerns the video path.
**Why**: Building real private video delivery (signed URLs, a CDN, DRM) is out of scope for a hackathon prototype and would be premature infrastructure. YouTube's iframe player gets a working, embeddable, responsive video player with zero backend video-serving code. "Unlisted" only means the video is unlisted on YouTube itself — it is **not** access-controlled by our app's auth; anyone with the link (leaked or guessed) can view it. This must not be described as private/secure content, and it is not suitable for anything requiring real confidentiality.
**Status**: Active for the prototype. **Migration note**: because only an opaque `video_id`/key is stored on the lesson row (never the file), swapping this for private object storage + CDN/signed URLs later only changes how that key is resolved into a playable URL — it does not require changing the `lessons` table shape or the LMS content hierarchy.

### 13. PDF/slides lessons: upload through Express, read via short-lived signed URLs

**Decision**: The `lesson-content` Supabase Storage bucket is **private** (`public: false`). Uploads go `client → Express (multipart, `multer`) → supabaseAdmin.storage.upload()`; the client never gets direct Storage write access, per ARCHITECTURE.md §8. Reads work differently: Express checks the caller is authenticated (any role can read; RLS-equivalent same as lesson content generally) and then calls `supabaseAdmin.storage.createSignedUrl()` with a 60-second TTL, returning that URL to the client — the actual file bytes then flow straight from Supabase's CDN to the browser, not proxied through Express.
**Why**: Proxying PDF bytes through Express would work but wastes Express's bandwidth/memory for no security benefit once the authorization decision (does this caller get a URL at all) has already been made — the same reasoning already applied to lesson video in Decision #12's "don't proxy the video" note. A private bucket + short-lived signed URLs keeps the actual authorization check server-side (a leaked signed URL only works for 60 seconds) while still letting large files be served efficiently. This is a read-only exception to "clients never call Supabase directly" — the client calls Supabase's CDN with a token Express minted, not Supabase's API with its own credentials, and it can never do so without Express's say-so first.
**Status**: Active.

### 14. Interactive lessons: `lessons.interactive_config` as jsonb, one exercise type (`matching`) to start

**Decision**: A `content_type: 'interactive'` lesson stores its exercise definition in a new `lessons.interactive_config` jsonb column rather than a normalized table (e.g. `interactive_exercises` + `interactive_exercise_items`). Only one exercise type exists so far — `matching` (term ↔ definition pairs, rendered client-side as a tap-to-pair exercise, graded client-side since there's no "submission" concept for it, unlike a quiz). The zod schema (`interactiveConfigSchema`) is a discriminated union on `type`, currently with one member, so adding a second exercise type is a compile-time-visible change (every `switch`/consumer has to handle it), not a silent JSON shape drift.
**Why**: PRD only requires "at least one genuinely interactive element," not a general-purpose exercise-authoring system — building normalized tables for a still-hypothetical second/third exercise type would be exactly the kind of premature abstraction `CLAUDE.md` says to avoid. jsonb keeps the DB shape stable while the exercise-type roster is still unknown; if a second type needs its own indexed queries later (not just "fetch by lesson"), that's the trigger to normalize, not before.
**Status**: Active. Revisit if a second interactive exercise type needs querying/reporting beyond "attached to this lesson."

### 15. Assessment questions: no RLS read policy at all; correct answers stripped in Express, not in the database

**Decision**: `assessment_questions` is the one content table in this codebase with **no** authenticated-read RLS policy — every other F3/F4 table (`courses`, `modules`, `lessons`, `content_translations`, `assessments`) got one. All reads of `assessment_questions` go through `supabaseAdmin` in Express: the admin/trainer authoring routes (`GET /assessments/:id/questions`) return the full row including `correct_option_id`; the trainee-facing route (`GET /assessments/:id/take`) builds a new object per question naming only the safe fields (`id`, `assessment_id`, `question_text`, `options`, `position`) — `correct_option_id` is never spread into the response. Grading (`POST /assessments/:id/attempts`) also reads the table via `supabaseAdmin` to compare submitted answers against `correct_option_id` server-side, then inserts the graded `assessment_attempts` row via `supabaseAdmin` too, rather than `req.supabase` — unlike every other own-row insert in this codebase (nominations, lesson_progress), which do use the caller's own RLS-scoped client.
**Why**: Postgres RLS is row-level, not column-level. A policy letting a trainee `SELECT` their own module's questions would have no way to hide just the `correct_option_id` column while allowing the rest — the policy would have to leak the answer key to give any read access at all. Since the correct answer must never reach the browser before grading, the only sound options were per-column Postgres `GRANT`s (real but heavier machinery, and this table has no other consumer that would benefit from it) or keeping this table entirely behind the service-role client and filtering in application code, where the "strip this field" logic is a one-line, easily-reviewed operation. The attempt insert uses `supabaseAdmin` for a related reason: correct grading requires reading `correct_option_id` in the same request handler regardless, so there was no security benefit left to gate the insert through a separate RLS-scoped client — `trainee_id` is still always taken from `req.user`, never the request body, so a trainee still can't submit as anyone else.
**Status**: Active. This is a deliberate, narrow exception — every other table added for F3/F4 does get an authenticated-read RLS policy per the established default (DATABASE.md).

### 16. Face embedding extraction runs in the browser (`apps/web`), not the Express service — amending #5

**Decision**: `@vladmandic/human` still does face detection/embedding extraction (the library choice in #5 is unchanged), but that extraction now runs client-side in `apps/web` (browser, WebGL backend) rather than server-side in Express as #5 originally described. A trainee's browser captures a webcam frame, runs Human locally, and sends only the resulting 512-number embedding array to Express — never a raw image. Express's face-rec responsibilities become: verify recorded consent, store the embedding (`face_embeddings`, own-row RLS), and — critically — always **recompute** the match server-side (cosine similarity against the trainee's own stored embedding(s)) rather than trusting any client-reported match result, per `CLAUDE.md`'s "never trust a client-reported ... face-match result" rule. The client only ever supplies the raw embedding, never a match score or a pass/fail verdict.
**Why**: Tried the server-side path first and it doesn't work on a stock Windows dev machine. `@vladmandic/human`'s Node build has two options: (1) `@tensorflow/tfjs-node` (native bindings) — a real install attempt failed outright (`npm install @tensorflow/tfjs-node`) because no prebuilt binary exists for this Node/ABI combination and the fallback native compile needs Visual Studio's C++ build tools, which aren't installed and aren't something to demand of every dev machine for a prototype; (2) the WASM Node build (`@vladmandic/human/dist/human.node-wasm.js`, no native compilation) — this **does** install and load cleanly, but a real end-to-end test (a photo with multiple clearly visible faces, run through blazeface detection) returned zero face detections while the same pipeline's body detector (movenet) correctly found a person in the same frame — a reproducible wasm-backend-specific failure in the face detector, not a config mistake (confirmed by lowering `minConfidence` to 0.05 and still getting zero results). Since Human is fundamentally built, tested, and documented as a browser-first library (WebGL backend), and the trainee's device already needs camera access for this feature regardless, running extraction in `apps/web` sidesteps both failure modes entirely and is arguably better for the DPDP Act's data-minimization principle besides — the raw camera image never has to leave the trainee's device at all, only the derived embedding does.
**Status**: Active. If mobile (`apps/mobile`) later needs face check-in, the same "extract on-device" approach applies there too (Human also runs in React Native), not a return to server-side extraction. Revisit if a future accuracy/consistency problem specifically requires centralizing extraction.

### 17. Chatbot embeddings: a local model (`Xenova/all-MiniLM-L6-v2`), not a hosted embedding API

**Decision**: F7's RAG retrieval generates embeddings **locally inside the Express service** using `@huggingface/transformers` (Transformers.js) with `Xenova/all-MiniLM-L6-v2` — 384 dimensions, mean-pooled and L2-normalized. This resolves the long-standing open question that `chatbot_corpus_chunks.embedding vector(1536)` was a placeholder for; the F7 migration recreates that column as `vector(384)`. Answer _generation_ still uses the Claude API (`claude-opus-5`) per PRD §10 — only the embedding half is local. Retrieval itself is a Postgres function (`match_corpus_chunks`) using pgvector's cosine operator, called from Express via `supabase.rpc()`, because PostgREST's query builder cannot express `<=>`.
**Why**: Anthropic has no first-party embeddings API (their documented recommendation is Voyage AI), so "use Claude for embeddings too" was never an option — the real choice was between a second paid vendor (Voyage/OpenAI) and a local model. Local wins here on four counts: (1) **one key instead of two** — F7 already requires an `ANTHROPIC_API_KEY` for generation; a hosted embedding provider would add a second account, key, and bill to a project that has no committed API budget; (2) **no per-query cost or rate limit** on the highest-frequency operation in the feature (every question embeds, and every corpus chunk embeds once); (3) **it works offline once cached**, which is directionally right for a platform whose stated non-functional requirement (PRD §7) is low-bandwidth rural usability; (4) **verified quality and installability before committing** — a spike embedded a representative domain query and scored 0.87 cosine against a relevant sentence vs 0.02 against an unrelated one, then live retrieval against the real database ranked a dairy-programme chunk first at 0.731 for a dairy question, with the next-nearest at 0.404. Install was checked explicitly against the trap that burned F5: the package installs cleanly on this Windows machine and runs on the WASM backend without `onnxruntime-node`'s native binaries (their build scripts are declared off in `pnpm-workspace.yaml`), so there is no repeat of DECISIONS.md #16's native-compilation dead end.
**Status**: Active. **Migration note**: the swap cost to a hosted provider later is small and well-contained — `embedText()` in `apps/api/src/chatbotService.ts` is the only place embeddings are produced, so switching means changing that one function, changing `EMBEDDING_DIMENSIONS`/`EMBEDDING_MODEL` in `packages/constants`, and running a migration that recreates the column and the RPC signature at the new dimension (plus re-embedding the corpus, which is cheap at this size). Retrieval SQL, route shapes, and the answer-generation path are all dimension-agnostic and would not change. Worth revisiting if retrieval quality proves insufficient on a real corpus — MiniLM is a small model, and Voyage's domain models would be the first upgrade to try.

### 18. Self-hosted lesson video via Cloudflare R2 (presigned URLs) — supersedes #12's YouTube-only approach

**Decision**: Course video lessons can now carry either a YouTube `video_id` (the original #12 approach, unchanged for existing content) or an R2 `storage_path`, mutually exclusive in practice on the same `lessons` row — no schema migration needed since `storage_path` already existed, shared with the PDF/slides upload path. Video bytes never transit Express: `POST /lessons/:id/video-upload-url` (admin/trainer) mints a presigned S3-compatible PUT URL against R2 via `@aws-sdk/client-s3`/`@aws-sdk/s3-request-presigner`, the browser uploads straight to R2 with it, then the caller attaches the resulting key with the existing `PATCH /lessons/:id`. Playback mirrors this with a presigned GET (`GET /lessons/:id/video-url`), same pattern as #13's PDF/slides signed reads.
**Why**: YouTube hosting (#12) requires content to already be public/unlisted on YouTube, which doesn't fit institution-authored training material that may not belong on a public video platform at all. R2 was chosen over Supabase Storage (already used for PDFs/slides, #13) specifically because video files are large — buffering a multi-hundred-MB upload through Express's memory the way the 25MB PDF path does (`multer`, in-memory) doesn't scale — and R2 has **zero egress fees**, which matters for a platform whose content gets streamed repeatedly by trainees on limited connections (PRD §7). This is the same narrow exception to "clients never call storage directly" that #13 already established: the client only ever talks to R2 with a token Express minted, never with its own credentials, and cannot get one without Express's say-so first.
**Cost tradeoff, stated plainly**: R2's free tier (10 GB storage, 1M Class A ops/month, 10M Class B ops/month, $0 egress always) is generous for a prototype, but unlike Backblaze B2 — the other candidate considered — **R2 has no hard spending cap**. Cloudflare only offers non-blocking budget-alert emails past a configured threshold; nothing stops usage automatically. B2 has a real, enforced daily cap. R2 was chosen anyway because free egress matters more here than a hard cap does at this scale, but this is a real operational gap someone should set a budget alert for (see manual setup steps given to the user), not an oversight.
**Status**: Superseded by #20 — moved from R2 to Backblaze B2 before any real credentials were ever configured, so nothing in production depended on R2 specifically. The presigned-URL architecture this entry describes is unchanged; only the storage provider changed.

### 19. Mobile app rebuilt on Capacitor, not React Native/Expo — supersedes #3's rationale for `apps/mobile`

**Decision**: `apps/mobile` is now a Vite + React web app (the same stack as `apps/web`, not React-Native-Web — see below) wrapped in a native Android shell via Capacitor (`@capacitor/core`, `@capacitor/android`, `@capacitor/cli`). The Expo/React Native starter that previously occupied `apps/mobile` (`App.tsx`, `app.json`, `expo`/`react-native` dependencies, `eslint-config-expo`) is removed entirely, not kept alongside the new setup. `capacitor.config.ts` points `webDir` at the Vite build output; `npx cap sync android` copies that build into the native `android/` project (committed to version control, per Capacitor's convention — it isn't fully regenerable from config the way Expo's managed `ios`/`android` folders were).
**Why**: #3's justification for a separate React Native codebase was specifically "camera/NFC/offline-native trainee screens on mobile." That premise turned out to be false: this project's face-recognition attendance uses an ESP32-CAM and its NFC card reads use a dedicated hardware reader, both integrated on the **web** side (an institution's front-desk/kiosk terminal), never the trainee's own phone. Once camera and NFC access are off the table, the only things `apps/mobile` actually needs per PRD §6.9 are: download course videos/quizzes for offline use, take quizzes offline, queue progress/attendance writes locally, and sync on reconnect (`last-write-wins`, unchanged from #7). None of that requires native UI — a WebView-wrapped web app can do all of it via Capacitor's `@capacitor/filesystem` (downloads) and a SQLite plugin (offline queue, not yet added — see Missing below), and doing so lets `apps/mobile` reuse `apps/web/src/trainee/*`'s screens (already built, already backend-verified) instead of rebuilding an entire second UI from scratch in React Native, which is what made F9 the flagged highest-complexity remaining MVP module in the first place. This is a direct, deliberate reversal, not silent drift — recorded here per this file's own rule, and discussed with the user before building (mobile architecture was raised, reasoned through, and approved before any code changed).
**Not React-Native-Web**: this doesn't reopen #3's Web/RN-Web question — `apps/web` (admin/employer dashboards) and `apps/mobile` (trainee-only, Capacitor-wrapped) remain genuinely different apps for genuinely different audiences; they just now share the same underlying framework (Vite/React) and, going forward, are expected to increasingly share actual trainee UI code, not only the `packages/*` logic layer #3 originally scoped the sharing to.
**Status**: Active, but scaffold-only so far. **Built**: the Capacitor + Vite shell itself, real Supabase Auth sign-in against the live API (`GET /api/profile`), a minimal authenticated home screen, and a generated, buildable `android/` native project (verified: `tsc -b` and `vite build` both clean; `npx cap add android` succeeded). **Missing** (tracked in `docs/IMPLEMENTATION.md`'s F9 entry, not silently assumed done): the actual trainee screens (lessons, nominations, certificates, jobs) haven't been ported from `apps/web/src/trainee/*` yet; no offline storage is wired up (`@capacitor/filesystem` and a SQLite plugin aren't installed yet — deliberately not added until the feature that uses them is actually built, per this repo's "don't add a dependency ahead of the code that needs it" convention); no forgot-password flow on mobile yet (needs Capacitor deep-linking, noted in `LoginForm.tsx`); and building a real APK needs the Android SDK, which isn't present in this dev environment — `npx cap add android` succeeded (that step doesn't require the SDK), but `./gradlew assembleDebug` does, so producing an actual `.apk` is a manual step for whoever has Android Studio installed.

### 20. Lesson video storage moved from Cloudflare R2 to Backblaze B2 — supersedes #18's provider choice

**Decision**: Same presigned-URL architecture #18 already built (`POST /lessons/:id/video-upload-url` mints a presigned PUT, `GET /lessons/:id/video-url` mints a presigned GET, both via the AWS S3 SDK against an S3-compatible endpoint) — only the provider underneath changed, from Cloudflare R2 to Backblaze B2. `apps/api/src/r2Client.ts` is replaced by `apps/api/src/b2Client.ts`; env vars changed from `R2_ACCOUNT_ID`/`R2_ACCESS_KEY_ID`/`R2_SECRET_ACCESS_KEY`/`R2_BUCKET_NAME` to `B2_ENDPOINT`/`B2_KEY_ID`/`B2_APPLICATION_KEY`/`B2_BUCKET_NAME`. The api-client function that used to be named `uploadLessonVideoToR2` is renamed `uploadLessonVideoFile` — provider-neutral, since nothing about the client side is actually R2- or B2-specific, only the signed URL it's handed is.
**Why**: #18 already documented R2's real gap honestly — no hard spending cap, only non-blocking budget-alert emails — and named B2 as the alternative that does have one. Since no real R2 credentials were ever configured (the feature shipped as scaffold-only, per #18's own status), switching before going live cost nothing and closes that gap for real rather than living with it. B2's free tier (10 GB storage, 2500 Class A + 2500 Class B "download" transactions/day free, egress free up to 3x stored data monthly) is comparable to R2's for this project's scale, and its S3-compatible API means the swap was almost entirely a rename, not a rewrite — the presigned-URL flow, the "video bytes never transit Express" reasoning, and the client upload/playback shape from #18 all carry over unchanged.
**Status**: Active, and **live-verified end-to-end against the real bucket**: real credentials were supplied, a real file was PUT to a presigned URL, attached to a real lesson, read back through a presigned GET, and the fetched bytes were byte-for-byte confirmed to match the upload — not just confirmed by code review or mocks. `B2_ENDPOINT`/`B2_KEY_ID`/`B2_APPLICATION_KEY`/`B2_BUCKET_NAME` are set in `apps/api/.env` (documented in `.env.example`); without them, video routes return 503, every other route is unaffected. `B2_ENDPOINT` is copied verbatim from the bucket's page in the B2 dashboard (`b2Client.ts` extracts the region from it for SigV4 signing rather than asking for a second, driftable env var). The trainee-playback gap #18 flagged is closed: `TraineeLearnLessons.tsx` calls `GET /lessons/:id/video-url` when a video lesson has no `video_id`, and `SelfHostedVideoPlayer.tsx` renders the result; `AdminCourseManager.tsx` has an actual "Upload Video File" control (progress bar, presigned PUT, then attaches the key via `PATCH /lessons/:id`). **One real gap found during live verification**: `updateLessonSchema.storage_path` is `z.string().optional()`, not `.nullable()` — there is no way to explicitly clear a lesson's `storage_path` via the API; an empty string works as a practical stand-in (every consumer treats it as falsy, identical to unset) but isn't a designed "detach" affordance. Not fixed yet — noted for whenever a "remove video" admin control is built. A small leftover test object (~20 bytes) remains in the live bucket from this verification; there is no delete route yet to clean it up automatically.

### 21. Face-recognition attendance moves to ESP32-CAM-fed kiosk capture — amends #5/#16, narrows F5's trainee-facing scope

**Decision**: Trainee self-service face check-in via the browser's own camera (`FaceCapture.tsx`, `getUserMedia` + client-side `@vladmandic/human` extraction, per #16) is superseded as the production check-in path. Face-recognition attendance instead runs from an ESP32-CAM (external hardware) feeding frames into the web app at an institution-operated kiosk/front-desk terminal — trainees do not use their own device's camera for face check-in at all, on either web or mobile.
**Why**: Confirmed directly with the user — the real hardware plan for this project pairs an ESP32-CAM (attendance) and a dedicated NFC reader (profile lookup) with the web client, both operated at an institution's kiosk, not on a trainee's personal device. `FaceCapture.tsx`'s current `getUserMedia`-based flow was built earlier in this project before that hardware context was known to whoever was building it at the time, and worked correctly as designed then — it just isn't the intended production path once the real hardware is accounted for.
**Practical effect, not yet built**: (1) `TraineeAttendance.tsx`'s embedded `FaceCapture` should eventually be removed from the trainee's own portal — trainee self-service attendance stays QR-code check-in only, already the other supported path. ### 23. Offline mode (F9's real remaining scope) — storage via Preferences + Filesystem, not SQLite

**Decision**: F9's offline layer lives in `apps/web/src/offline/` (not `apps/mobile` — that package has no `src/` per #22), consumed by the trainee-facing screens that need it. Four pieces: `storage.ts` persists a write-queue and a downloaded-lesson manifest as JSON via `@capacitor/preferences` (not `@capacitor-community/sqlite`); `network.ts` exposes `useOnlineStatus()` via `@capacitor/network`; `downloadManager.ts` downloads a self-hosted video lesson's file to `@capacitor/filesystem`'s `Directory.Data` (video only, not PDF/slides — see Why); `syncManager.ts` provides `enqueueWrite()` and `useAutoSync()`, which flushes the queue in order against the same real endpoints (`updateLessonProgress`, `submitAssessmentAttempt`, `checkInWithQr`) the moment the app comes back online, stopping at the first failure rather than skipping past it so ordering is never violated.
**Why Preferences over SQLite**: the actual data here — a queue of pending writes, a small manifest of downloaded lesson IDs — is a JSON array, not a relational dataset that benefits from SQL querying. `@capacitor-community/sqlite`'s web implementation needs a bundled WASM binary and a `jeep-sqlite` custom element just to run in a browser at all; Preferences has a real native and web implementation with none of that setup. CLAUDE.md is explicit about not reaching for more machinery than the data shape actually calls for, and a write-queue of at most a few dozen small JSON objects is comfortably within Preferences' intended range.
**Why video-only downloads, not PDF/slides too**: PRD §6.9 names "download course videos" specifically, and video is the one case where DECISIONS.md #13's existing signed-URL-read pattern doesn't already work offline (a PDF read still needs a live signed URL each time). Adding offline PDF caching "for symmetry" with nothing in the PRD asking for it, and no user story motivating it, is exactly the gold-plating CLAUDE.md warns against — left out on purpose, not an oversight.
**Why quiz grading stays server-side even when offline**: an offline quiz submission is queued as raw answers (`quiz_attempt`), never scored client-side — CLAUDE.md's "never trust a client-reported quiz score" rule doesn't get an offline exception. Shipping the correct-answer key to the device so it could grade itself offline would be a real integrity hole; the trainee sees "saved, pending sync" instead of an instant score, and the real score only exists once `syncManager` actually reaches the server.
**Known limitation, stated plainly**: downloads are not resumable — `Filesystem.downloadFile` re-downloads from the start if interrupted, unlike a true chunked/range-based resumable transfer. Real given PRD §7's low-bandwidth context, but building actual HTTP-range resume was judged more machinery than this round needed; noted as a real follow-up, not silently assumed solved.
**A second real gap found and fixed in the same round, not left as a surprise**: wiring the plugins into `apps/web/package.json` alone was not sufficient — `cap sync`'s native-plugin discovery scans the package.json of the directory it's run from (`apps/mobile`), not `apps/web`'s, so the three plugins were invisible to the native Android project until also added to `apps/mobile/package.json`. Confirmed via `cap sync`'s own output ("Found 3 Capacitor plugins for android") and by inspecting the generated `app/capacitor.build.gradle` directly, not just trusting a clean exit code.
**Status**: Active, and live-verified through an actual `./gradlew assembleDebug` build (not just `tsc`/`vite build`) — a real, installable `app-debug.apk` was produced with the offline module and all three native plugins correctly linked in. **Not yet done**: an actual on-device test of the full offline→reconnect→sync loop (needs a real phone or emulator, tracked the same way as F9's other device-dependent gaps); resumable downloads (see above); and the two remaining screens (`TraineeHome`, certificates) haven't been reviewed for their own offline needs beyond what PRD §6.9 explicitly names (lessons, quizzes, attendance).

### 24. Hosting: Render (Web Service for `apps/api`, Static Site for `apps/web`) — resolves ARCHITECTURE.md §15's `TBD`

**Decision**: `apps/api` deploys to Render as a Node **Web Service** (repo root as the build context — the pnpm workspace needs `packages/*` resolvable, so the service cannot be rooted at `apps/api` alone; build command runs `pnpm --filter api build`, start command `pnpm --filter api start`). `apps/web` deploys to Render as a **Static Site** (`pnpm --filter web build`, publish `apps/web/dist`), with `VITE_API_URL` set to the deployed API's Render URL as a **build-time** env var (Vite bakes `VITE_*` vars into the bundle at build time, not read at runtime — the same fact that caused the LAN-IP mobile bug this decision also permanently fixes, see below). `apps/mobile` gets no separate Render deployment — per Decision #22 it has no `src/` of its own and just wraps whatever `apps/web/dist` was built with, so pointing that build at the real HTTPS Render API URL instead of a LAN IP is what actually fixes the Android app for good.
**Why Render over the alternatives already on the table** (Cloudflare/Backblaze were evaluated for storage, not compute): free tier covers both a Node web service and a static site with no credit card required for the static site, native Git-push-to-deploy with no extra CI tooling needed (resolving the "no CI/CD pipeline exists yet" gap partially — deploys are still manual-trigger, not test-gated, so that half of the `TBD` stays open), and it needs zero Dockerfile or infra code for a plain Node + Vite monorepo — matching this project's "minimal, not gold-plated" rule better than standing up Kubernetes/ECS for a hackathon prototype.
**Two real, pre-existing risks found and fixed in this same round, not discovered by deploying blind**:

1. Root `package.json`'s `engines.node` was `">=20"`, but `apps/api` importing `@ncct/constants`/`@ncct/shared-types`/`@ncct/validation` (each `"main": "src/index.ts"`, i.e. shipped as raw TypeScript, never compiled — there is no separate build step for `packages/*`) only works at runtime because Node's _native_ TypeScript type-stripping resolves those `.ts` files directly. That behavior is not available, at any Node 20.x version — it shipped experimentally in 22.6, and only became **default-on** starting at 22.18.0 (LTS) / 23.6.0. A Render service provisioned on Node 20 (a very plausible default for an unpinned `engines` field) would have built successfully (`tsc` doesn't care) and then **crashed immediately on boot** trying to `import` a `.ts` file it can't parse — a failure mode that only appears in production, never locally, since local dev always ran on Node 24.13.0. Fixed by raising `engines.node` to `>=22.18.0` and adding a root `.node-version` file (`22.18.0`) so Render's Node buildpack picks a compatible version without relying on the `engines` field being read correctly by every tool in the chain. Verified locally, not assumed: ran the actual production path (`pnpm --filter api build && node dist/index.js`, no `tsx`) and confirmed it boots and serves `/health` correctly — the workspace-package imports resolve via the same native stripping mechanism this decision now guarantees a compatible Node version for.
2. No `packageManager` field existed, so a fresh Render build environment had no guarantee of getting the same pnpm version (11.24.0) this project was built and tested against; a pnpm major-version drift can change lockfile resolution behavior. Fixed by adding `"packageManager": "pnpm@11.24.0"` so `corepack enable` (Render's documented way to get pnpm) activates the exact pinned version.
   **Not changed**: CORS (`cors()` with no options, already wide-open) — no code change needed since there's no cookie-based session to leak; every authenticated request already carries an explicit bearer token, so an open CORS policy doesn't weaken anything the JWT check doesn't already guard. `PUBLIC_WEB_URL` (used only for the QR check-in link, Decision in F5's entry) is a plain env var update once the web Static Site's real URL is known — no code change.
   **Status**: Active. Deployment steps and current URLs are operational detail, not architecture — not duplicated here; ask if they're not already in hand.

### 29. P6 Deep Training & Learning Analytics (dropout-risk) promoted from Phase-2 into MVP scope

**Decision**: PRD §13's "deep Training & Learning Analytics (predictive/dropout-risk)" is built and shipped as a new `dropoutRisk` dimension on the existing `GET /api/analytics/dashboard` (F8) response — no new route, no new table, same "computed at request time from other features' own tables" design F8 already established. For every `approved` nomination, `analyticsService.ts` computes three signals purely from data F2–F5 already store — lesson-completion rate (via the `courses → modules → lessons` chain, matched against that trainee's `lesson_progress`), timetable-attendance rate (sessions so far for the programme vs. that trainee's `attendance_records`), and days since any activity (falling back to `nominated_at` so a freshly-nominated trainee is never penalized on day one) — plus a count of failed `assessment_attempts` under that programme, and combines them into a heuristic 0–100 `riskScore` and a `low`/`medium`/`high` `riskLevel`. **Why**: explicit user request, same round as P3.
**This is explicitly a heuristic flag, not a trained prediction** — the "predictive" half of PRD §13's phrasing is not literally true of what shipped, and that's stated in-product (`AnalyticsDashboard.tsx`'s dropout-risk section subtitle) as well as here: there is no historical dropout data in this project to train or validate a real model against, so a hand-tuned rule (thresholds in `packages/constants`: `DROPOUT_RISK_LOW_COMPLETION` 0.25, `DROPOUT_RISK_LOW_ATTENDANCE` 0.5, `DROPOUT_RISK_STALE_DAYS` 14, medium/high score cutoffs 30/60) is the honest MVP version — same category of unvalidated-starting-point judgment call as `FACE_MATCH_THRESHOLD`/`CHATBOT_MIN_SIMILARITY`, flagged for the same reason: revisit once real outcome data exists to tune against.

**UI color choice**: the three risk levels are a _status_ palette (state: good/warning/critical), not the dashboard's existing categorical `--chart-1/2/3` set (identity: programme mode, funnel status) — per the dataviz skill's "color follows the job" rule, they reuse this app's existing reserved status tokens (`status-shortlisted`/`status-pending`/`status-rejected`, already used for shortlisted/pending/rejected pills elsewhere) rather than inventing a fourth palette, and each level ships with an icon + label, never color alone.
**Status**: Active. Unit-tested (`apps/api/src/analyticsService.test.ts`, 10 new tests: ignores non-approved nominations, flags low completion/low attendance independently, only counts attendance/failed-attempts against the trainee's _own_ programme — not another trainee's or another programme's rows landing on the wrong trainee, failed-attempt scoring capped at 3, a fresh nomination is never stale on day one, staleness alone stays low-risk but combines with another signal to cross into medium, sorts `flagged` by score descending). **Live-verified against the real API + real Supabase project**: a throwaway trainee nominated and approved into a programme with one authored lesson (no progress) and one past session (no attendance) correctly scored 70/`high` (40 completion + 30 attendance, exactly as designed) in the _real_ dashboard response — and two pre-existing real trainees from earlier sessions' data also showed up flagged at `medium` with real, previously-uncomputed completion/attendance numbers, confirming this reads real historical data correctly, not just synthetic test rows.

### 30. F10 NFC Profile Card: static UID + rotatable URL code, two independent lookup keys on one physical card

**Decision**: A trainee's NFC card carries no personal data at all — it is a pointer, not a record. Two lookup paths, deliberately kept independent:

- **Phone-tap path** (any phone, no app, no login): the card is written once, at issuance, with a static NDEF URI record pointing at `{PUBLIC_WEB_URL}/?profile={code}`. `App.tsx` reads `?profile=` before the auth gate — same placement and reasoning as the pre-existing `?verify=` certificate check — and renders the new no-auth `GET /api/public-profiles/:code` route (`apps/api/src/routes/publicProfile.ts`), which mirrors `certificates.ts`'s public-lookup pattern exactly (`supabaseAdmin`, no `requireAuth`).
- **Kiosk path** (staff-operated, PN532/RC522 hardware): the tag's factory UID (unwritable, always present regardless of tag type) is bound to a trainee via `PUT /api/profiles/:traineeId/nfc-tag` (admin/trainer-only) and resolved via `GET /api/kiosk/nfc-lookup/:uid` (admin/trainer-only). This route deliberately does **not** check `public_profile_enabled` — that flag gates the open internet, and staff already see trainee records through the existing admin UI, so gating an internal kiosk tool on it would be theatre, not privacy.

`profiles.public_profile_code` is 16 alphanumeric characters (vs. certificates' 8) from the same transcription-safe alphabet (`codeGenerator.ts`, extracted out of `certificateService.ts` so both share it) — deliberately longer because this code is never hand-transcribed, only ever traveling inside an NFC-written URL, so it can afford to make enumeration infeasible without needing rate limiting for MVP. `profiles.nfc_tag_uid` is separate and nullable — a lost card is handled by two independent, composable levers: rotating the URL code (kills the phone-tap path instantly, `POST /profiles/me/card`) and/or nulling the UID (kills the kiosk path, same PUT route with `nfc_tag_uid: null`).

**Why this consent flag is separate from `visible_to_employers`**: `visibility_settings.public_profile_enabled` is its own column, not a reuse of the pre-existing employer-visibility flag, because the two gate genuinely different audiences under the DPDP Act 2023 — an employer-portal audience sits behind a login; this gates the open, unauthenticated internet. A trainee should be able to consent to one without the other.

**Why skills are derived, not stored**: no dedicated skills taxonomy exists on the public-profile response — same reasoning `employerSearch.ts` already documented (DECISIONS.md context on that route): programme titles behind a trainee's earned certificates are the one legitimate "what is this trainee credentialed in" data source that exists, so the public profile and kiosk routes both derive `skills` from `certificates → programmes(title)`, deduplicated, rather than inventing a second taxonomy alongside P1's real one (#26).

**Why opted-out and unknown codes return the same 404**: a differently-coded response (e.g. 403 for opted-out vs. 404 for unknown) would let anyone probe which codes are real, leaking exactly the membership fact the opt-out is meant to protect. Both cases in `publicProfile.ts` fall through to an identical `{ error: "Profile not found" }` 404.

**Hardware**: no ESP32-CAM dependency (unlike F5/#21) — a card reader (PN532 or RC522, both confirmed working over SPI in this project's own hardware testing) only needs to report a UID string, which both chip families do natively. The kiosk terminal (`KioskNfcReader.tsx`) reads that UID over **Web Serial** from a USB-tethered reader, not by polling an `http://` endpoint on the reader's own WiFi — chosen specifically because Web Serial requires a secure context (satisfied by this site's HTTPS deployment per DECISIONS.md #24), sidestepping the mixed-content block that an `http://192.168.x.x` WiFi-reader design would hit against the deployed site.

**Status**: Built. Migration `20260901000014_f10_nfc_profile.sql` applied directly to the live Supabase project. `apps/api/src/routes/publicProfile.ts` (4 routes: public lookup, card issuance, kiosk lookup, tag binding) and an extension to `visibilitySettings.ts` (`PUT /visibility-settings/public-profile`), unit-tested (`publicProfile.test.ts`, 19 tests: no-auth confirmed, unknown/opted-out/disabled-all-404-identically, own-row scoping via `req.user` not the request body, uid normalization, 409 on a UID already bound elsewhere). Web: `PublicProfile.tsx` (mobile-first, per the reasoning that nearly every view of this page arrives from a phone that just read an NFC tag — the one screen in this app designed narrow-first rather than narrow-adapted), `NfcProfileCard.tsx` (trainee issuance UI, wired into `ProfileEditor.tsx`), `KioskNfcReader.tsx` (new `"kiosk"` tab, admin/trainer-only). `apps/web/index.html` gained a blanket `noindex, nofollow` — the whole app is one `index.html` with both this and the certificate-verification page reachable off it via query param, so a per-route noindex isn't possible; nothing else in this login-gated ERP should be indexed either. **Not yet live-hardware-verified**: the actual PN532/RC522 firmware exists and reads real UIDs on the bench (per this project's own hardware testing session), but the kiosk web page has not yet been run against real hardware end-to-end — the API/DB/web layers are unit-tested and typecheck/build clean, the hardware integration itself is the remaining verification step.

### 32. ESP32-CAM kiosk face check-in: capture-poll over plain HTTP, staff-authorized route names the trainee explicitly — resolves #21's open items

**Decision**: Three things #21 left open are now resolved. **(1) Wire protocol**: the ESP32-CAM runs a small custom sketch (`ESP32-CAM/arduino/kiosk_capture_server/`, not the stock `CameraWebServer` example) serving a single-frame `GET /capture` (JPEG) over plain HTTP — no MJPEG streaming, since the kiosk only needs ~1 frame/sec for detection, not video. It sends `Access-Control-Allow-Origin: *` (needed so the kiosk page can draw the fetched frame to a `<canvas>` and actually read its pixels — without it the canvas is cross-origin-tainted and `@vladmandic/human` cannot extract from it), `Connection: close`, and `Cache-Control: no-store` (a real bug found on real hardware: without these, the board's single-threaded `WebServer` produced stale frames roughly every 15-20s instead of on every request), and disables WiFi modem-sleep (`WiFi.setSleep(false)`) since a kiosk on wall power has no reason to trade latency for standby power savings. **(2) Mixed content**: since the ESP32-CAM cannot serve HTTPS, the kiosk terminal must load the web app from a local plain-`http://` origin (not the deployed HTTPS site) — a browser blocks an HTTPS page from fetching an `http://` resource. This is a kiosk-deployment/ops detail (serve `apps/web`'s build behind a local static server on the kiosk machine, `VITE_API_URL` still points at the real HTTPS API), not a code change. **(3) Identification**: confirmed the face check-in cannot reuse trainee-facing `POST /api/attendance` at all — that route infers the trainee from `req.user!.id`, and a shared kiosk terminal has no trainee JWT. A new staff-authorized route, `POST /api/timetable/:sessionId/kiosk-face-checkin` (`requireRole("admin","trainer")`), takes an explicit `trainee_id` in the body instead — same shift `publicProfile.ts`'s `GET /kiosk/nfc-lookup/:uid` route (#30) already made for the identical reason. Everything else about the match is unchanged from the trainee route: the server always recomputes `cosineSimilarity` itself, a below-`FACE_MATCH_THRESHOLD` match returns `200 { matched: false, fallbackToQr: true }` without writing a record rather than blocking or erroring, and the client only ever supplies the raw embedding it extracted locally (browser-side `@vladmandic/human`, reusing `FaceCapture.tsx`'s already-loaded singleton via a newly-exported `getHuman()`, fed a captured-frame `<canvas>` instead of a live `getUserMedia` video element).
**Why explicit `trainee_id` over inferring identity some other way**: the alternative (walk-up 1:N search — match the captured face against every enrolled trainee in the session's roster with no prior identification step) was considered and rejected as more than this project needs — it's real new backend work (broader query, materially worse false-match risk as roster size grows) for a UX gain (skip a tap/typed id) that isn't asked for anywhere in the PRD. Naming the trainee first (typed for now; a natural follow-up is chaining this from `KioskNfcReader.tsx`'s already-resolved NFC-tap lookup, not built in this round) keeps the face step what it already was for the trainee-facing flow: a verification, not an open-set identification.
**New surfaces**: `packages/validation`'s `kioskFaceCheckInSchema` (exports the previously-private `faceEmbeddingVectorSchema` for reuse); `apps/api/src/routes/attendance.ts`'s new route (8 new tests in `attendance.test.ts`, including that a `trainee`-role caller gets 403 — this route is staff-only, the opposite authorization shape of the route right above it in the same file); `packages/api-client`'s `kioskFaceCheckIn`; `apps/web/src/KioskFaceCheckIn.tsx`, embedded into `AttendanceManager.tsx` directly below the session-id input it shares.
**Status**: Active. Full workspace `typecheck`, `pnpm --filter web build`, and `pnpm --filter api test` (402 tests, all passing) all clean. ### 33. Kiosk hardware terminal: one combined screen over a single serial link, ESP32 DevKit as student-facing I/O — supersedes #32's open items and #30's separate-tab kiosk

**Decision**: The NFC tap and the face capture are now driven by hardware in one unattended flow, on one screen (`apps/web/src/KioskTerminal.tsx`, a new admin/trainer `"terminal"` tab), rather than by staff operating two separate tabs. A student taps a card, sees their own name on an OLED, positions themselves, presses one button, and gets a verdict — no staff interaction per student.

Three parts, with a deliberate split of responsibility:

- **ESP32 DevKit controller** (`ESP32-CONTROLLER/arduino/kiosk_controller/`) — RC522 reader, SSD1306 OLED, buzzer, capture button. A non-blocking `millis()` state machine (IDLE → IDENTIFYING → WAITING_FOR_FACE → VERIFYING → RESULT_HOLD) with per-state timeouts. It is pure I/O: **it never decides whether a face matched**, it reports events up and renders whatever verdict comes back (CLAUDE.md's never-trust-a-client-face-match rule applies to firmware too, not just the browser).
- **The browser** stays the brain, because it is the only part that can run `@vladmandic/human`: it resolves the UID via the existing `GET /api/kiosk/nfc-lookup/:uid` (#30/#31), fetches a frame from the ESP32-CAM's `/capture` (#32), extracts the embedding, and submits it to `POST /api/timetable/:sessionId/kiosk-face-checkin` (#32).
- **The API** is unchanged. This round added no route and no schema — it is purely a new front-end driver over surfaces #30, #31 and #32 already built, which is the reason it needed no new tests.

**Wire protocol**: newline-terminated ASCII, 115200 baud, both directions. Up: `UID:<hex>`, `BTN:CAPTURE`, `STATE:<name>`. Down: `NAME:<full name>`, `UNKNOWN`, `OK`, `FAIL`, `DUP`, `ERR:<text>`, `RESET`. Unknown lines are ignored rather than erroring, so either side can grow without a lockstep flash of the other.

**Why one screen instead of keeping #30's separate "NFC Kiosk" tab**: a serial port can only be held open by one holder at a time, and card taps and button presses arrive on the *same* cable. Two tabs cannot both hold it, so the hardware flow is impossible while the panels are split — this is a hard platform constraint, not a UI preference. `useKioskSerial.ts` owns the single connection (read loop plus a writer held for the connection's life); card *binding* moved onto the terminal for the same reason (switching tabs to bind an unrecognized card would mean dropping and re-granting the port).

**Why `http://localhost` specifically**: Web Serial requires a secure context, which plain `http://` on a LAN IP is not; and the ESP32-CAM serves plain HTTP, which an HTTPS page may not fetch (mixed content). `http://localhost` is the one origin that is both a secure context and able to fetch plain HTTP — so #32's hosting item and this one resolve to the same answer for two independent reasons. This closes #24's deployed-HTTPS assumption for the kiosk machine only; everything else still loads from the deployed site.

**Shared-code notes**: `kioskCapture.ts` extracts the camera path (`normalizeCamBase`, `captureFrame`, `extractEmbedding`, `withCaptureRetries`) as pure functions so the manual panel (`KioskFaceCheckIn.tsx`) and this terminal cannot drift on details that were expensive to get right on real hardware. Two of those constants are measurements, not guesses: `CAMERA_TIMEOUT_MS` is **20s** because the same 4KB QVGA frame was observed returning in 2.5s, 4.7s and 11.0s over this kiosk's WiFi — an earlier 8s value was aborting transfers that were completing normally — and `MAX_CAPTURE_ATTEMPTS` is 2 because every retry is another timeout the student stands there for. `packages/api-client` also gained an `ApiError` carrying `status`, because the terminal has to tell "already checked in" (409 → `DUP`, a *success* to show calmly) apart from a real failure (→ `ERR:`), which a bare `Error` message string could not express.

**Status**: Active. Verified on real hardware in stages: the controller's card-tap → OLED-name → button → capture sequence behaves as specified, and a real face through the real camera and real route records attendance (both user-confirmed on the bench). **Not yet reported back**: one full unattended run of the combined terminal with both dev servers up, end to end. One diagnostic worth keeping: an OLED stuck on "check the kiosk pc" means the browser isn't answering — in the one observed case the dev servers were simply down and the firmware was behaving correctly. **Known limits**: Chrome/Edge desktop only (Web Serial), carried forward from #30; the session id is still typed by hand on the terminal (there is no `devices` table or active-session concept — an open design question, not an oversight); and the yellow-LED "reposition yourself" feedback the wiring allows for would need on-board face detection (ESP-WHO) that this split deliberately does not use.

### 34. Kiosk consent gate moves to the identify step, and the controller's verify timeout is derived from the browser's capture budget — amends #33

**Decision**: Two corrections to #33's terminal flow, one legal/UX and one a timing bug, plus the controller sketch revised to the state names #33 already documented.

**(1) The DPDP consent gate now runs before the camera, not after it.** `GET /api/kiosk/nfc-lookup/:uid` gained a `face_enrolled` boolean (`packages/shared-types`' `KioskProfileResult`), computed from a `select("id").limit(1)` existence probe against `face_embeddings` — the vector itself is never returned, only whether a row exists. `KioskTerminal.tsx` checks it and sends `ERR:face not enrolled` instead of `NAME:<name>`, so a trainee without an enrolled face never reaches `WAITING_FOR_FACE` and the board never tells them to look at the camera. **Why "has an enrolled embedding" is the right proxy for consent**: `face_embeddings.consent_given_at` is `not null` in the initial migration and is stamped server-side at enrollment (`enrollFaceEmbeddingSchema` requires a literal `consent: true`), so a row cannot exist without recorded consent and there is no "enrolled but not consented" state to distinguish — one existence check answers both questions. **Why it matters that this moved earlier**: the outcome for the trainee was already correct before this change (the check-in route 400s with "No enrolled face embedding"), but only *after* the ESP32-CAM had been asked for a frame of their face and that frame had been run through Human in the browser. ARCHITECTURE.md §13's rule is about not processing biometric data without consent, not merely about not storing it, and a capture that is discarded is still a capture. The server-side check is unchanged and remains the real enforcement — this is a second, earlier layer, the same defense-in-depth shape as CLAUDE.md's "role middleware *in addition to* RLS".

**(2) `VERIFY_TIMEOUT_MS` is now 55s, derived rather than chosen.** The controller's verify window has to cover what the browser half actually takes, and the browser's worst case is dominated by `kioskCapture.ts`'s own measured constants: `MAX_CAPTURE_ATTEMPTS` (2) × `CAMERA_TIMEOUT_MS` (20s) = 40s of camera alone, plus Human's detect pass and the check-in round trip. A board that gives up first is not merely impatient, it is **wrong in the dangerous direction**: it shows "Check the kiosk PC", drops to `RESULT_HOLD`, and the `OK` that arrives moments later lands in a state that ignores it — the student reads an error for a check-in that *was* recorded, and `attendance_records` and the OLED disagree. The 25s value an earlier draft of this sketch carried would have fired on any capture that needed its retry at all. `kioskCapture.ts` now exports `VERIFY_BUDGET_MS` as the single documented source for that arithmetic, with both files pointing at each other. `IDENTIFY_TIMEOUT_MS` stays at the bench-tested 8s for the same reason in miniature: the lookup fans out to four Supabase queries and may hit a cold Render instance.

**(3) Sketch revised to match its own documentation.** The controller's states are now literally `IDLE → IDENTIFYING → WAITING_FOR_FACE → VERIFYING → RESULT_HOLD`, the names #33 recorded; the file had been carrying `READY_FOR_FACE`/`RESULT`. The beep vocabulary is now distinct per verdict (`OK` one short, `FAIL` two short, `DUP` one *soft* — "you're all set", not a failure — `ERR`/timeout one long), the OLED helper takes a third line so error text is readable, and the optional-LED scaffolding (three `#define`s pinned at `-1`, i.e. dead on every real build) is gone, since the OLED says more than a coloured light can. Retained from the previous sketch because removing them would have been a regression: the `CARD_COOLDOWN_MS` guard (belt-and-braces against one tap being read twice — the state transition is the real guard and `PICC_HaltA()` means a card left on the reader won't answer `REQA` again until it is lifted, so this is inert in the normal flow rather than load-bearing), `PCD_DumpVersionToSerial()` (a `0x00`/`0xFF` version register is how you find out the RC522 isn't on the SPI bus before a tap silently does nothing), and the `READY` boot marker.

**Status**: Active. Node 22 (matching `.node-version`) and pnpm 11.24.0 were installed on this machine via Homebrew/Corepack specifically to close out this entry's verification gap, and everything below actually ran, not just compiled. Firmware: a new logic harness (`ESP32-CONTROLLER/test/`, plain g++ against stub Arduino/RC522/SSD1306 headers — no toolchain or board needed) compiles the real sketch and drives its state machine with fake time, taps and serial input: 23/23 checks pass, covering every transition, both directions of the wire protocol, the UID hex formatting, all four timeouts, and that stray verdicts and unknown lines are ignored. Two of those checks are how item (2) was found rather than argued: set `VERIFY_TIMEOUT_MS` back to 25s and they fail — the board abandons the transaction at the browser's worst case and the `OK` that follows is dropped. The harness proves nothing about wiring, SPI, I2C or the real RC522; it is a reason to flash the board, not a substitute for doing so. TypeScript/API: `pnpm test` — 425/425 passing (40 files), including the three new `face_enrolled` cases in `publicProfile.test.ts`; `pnpm typecheck` clean across all 7 workspace packages; `pnpm lint` clean (two pre-existing oxlint Fast-Refresh warnings in unrelated files, not introduced here); `pnpm --filter web build` succeeds. **Still not done**: nothing was flashed to real hardware, and #33's outstanding item — one full unattended end-to-end run of the combined terminal — is still outstanding and now additionally wants the not-enrolled path walked deliberately (tap a card belonging to a trainee with no face enrolled; the OLED should read "Error / face not enrolled" and the camera should never be hit).

### 37. Certificates now key off course completion, not a single passing assessment — resolves the open question #29 (DATABASE.md) had carried since F4

**Decision**: A trainee is now issued one certificate per **completed course** — every lesson across every module of the course marked complete, and every module assessment in that course (if any) passed — instead of the previous behavior of minting a new certificate on every individual passing assessment attempt. Requested directly by the user ("as soon as you complete a course you get certificate"), and it resolves the exact open question `docs/DATABASE.md`'s certificates entry had flagged since F4 shipped: a programme with multiple per-module quizzes previously produced one certificate per passed quiz, not one per programme/course.

**Why course, not programme**: a programme (`programmes`) can contain multiple courses (`courses`), each with its own lesson/assessment content. Certifying at the programme level would mean a trainee finishing one course out of three in a programme gets nothing to show for it; certifying at the course level (the schema's actual unit of "a body of lessons + assessments") gives a real, checkable completion milestone per course while `programme_id` is still denormalized onto each certificate row (unchanged) so `skillGapService.ts`'s programme-level skill acquisition logic needed no changes at all.

**Schema** (`supabase/migrations/20260901000015_f4_course_completion_certification.sql`): `certificates` gains a required `course_id` (references `courses`, on delete cascade) and a new `certificates_trainee_course_unique` unique index on `(trainee_id, course_id)` — the mechanism that makes issuance idempotent. `assessment_attempt_id` is now **nullable**: a course with no assessments at all (pure lesson content) can still be completed and certified with nothing to point at; where a course does have assessments, the most recent passing attempt is still recorded there for audit purposes. The migration also **deletes every existing row in `certificates`** rather than attempting to backfill `course_id` for them — inspected the live table first rather than assuming: 8 rows existed, 3 of them already pointing at Storage objects that didn't exist (broken test fixtures from earlier verification rounds, not real data), none of them fitting the new one-per-course model. The corresponding 8 PDFs in the live `certificates` Storage bucket were also removed via the Storage API. This project remains prototype-scale with no real issued credentials, confirmed before deleting anything, not assumed.

**Implementation** (`apps/api/src/certificateService.ts`): `issueCertificateForPassingAttempt` (the old per-assessment trigger) is gone, replaced by `checkAndIssueCourseCertificate({ traineeId, courseId })` — the idempotent core: returns `null` immediately if this trainee is already certified for the course or if the course has no modules; otherwise walks `modules → lessons → lesson_progress` (every lesson needs a `completed_at`) and `modules → assessments → assessment_attempts` (every assessment needs a `passed: true` row), issuing the certificate only when both hold. ### 38. Timetable session check-in gets a short numeric code, alongside the existing UUID/QR

**Decision**: `timetable_sessions` gains a `check_in_code` column — a unique 6-digit numeric code, generated server-side at session creation — as a human-shareable alias for the session's real UUID. Requested directly by the user: sharing a raw session UUID between faculty, and having a trainee type one in by hand as the QR-check-in fallback, was a genuine, reported usability problem, not a hypothetical one.

**Why numeric, not alphanumeric**: the existing `generateCode` helper (certificate codes, F10's public-profile code) uses a letter+digit alphabet with ambiguous characters already excluded (`0/O/1/I`), which is the right choice for something read off a *printed* document. A session code's actual use is different — it's read aloud across a room or written on a whiteboard — and spoken letters have their own ambiguity a printed one doesn't (B/D, M/N). A 6-digit numeric code sidesteps that entirely; it's the same design Kahoot/Zoom/Google Meet join codes settled on for the identical scenario. `generateNumericCode` (`apps/api/src/codeGenerator.ts`) is a second, separate generator rather than a parameterized version of `generateCode`, since the two now have genuinely different alphabets for genuinely different reasons — folding them into one function with an alphabet flag would obscure why each exists.

**What didn't change**: QR check-in itself. The QR still encodes `{PUBLIC_WEB_URL}/?checkin={sessionId}` with the real UUID, exactly as before — scanning has never required typing anything, so the short code adds nothing there. `check_in_code` only replaces raw-UUID handling in the two places a human actually had to touch one: `AttendanceManager.tsx`'s faculty-facing session lookup (was a free-text "Session ID / UUID" field feeding `getAttendanceQr`/`getAttendanceRoster`/the kiosk directly; now a "Session Code" field that resolves to the real id via a new lookup route first) and `TraineeAttendance.tsx`'s manual fallback (same shape: resolve code → id → the existing `checkInWithQr` call, unchanged).

**Schema** (`supabase/migrations/20260901000016_timetable_session_checkin_code.sql`): `check_in_code text not null`, backfilled for existing rows via `row_number() over (order by random())` so the backfill can't collide with itself, then a unique index (`timetable_sessions_check_in_code_unique`). `POST /programmes/:id/timetable` generates the code at insert time and retries (up to 5 attempts) on a `23505` unique-violation — the only unique constraint on this table besides the primary key, so any conflict there is unambiguously a code collision, not some other write failing. A 6-digit keyspace is small enough (10^6) that this app's scale will effectively never see a real collision, but the retry loop is there for correctness regardless, not because it's expected to run.

**New route**: `GET /api/timetable-sessions/code/:code` (`requireAuth` only, no role restriction — same authenticated-read posture as the existing `GET /programmes/:id/timetable`) validates the 6-digit format, looks up by `check_in_code` via `req.supabase` (RLS-backed, same as the sibling timetable-read route), and returns the full session row or 404. `GET /timetable/:sessionId/qr`'s response also now includes `checkInCode` alongside `qrDataUrl`/`checkInUrl`, so the same call that generates the QR also hands back what to say out loud instead.

**Why this doesn't violate CLAUDE.md's "never trust a client-reported ... attendance status"**: read in context against how that rule is actually applied everywhere else in this codebase (quiz scores, face-match verdicts), it's about not trusting a *recomputable verdict* a client claims to have already produced — the server always independently recomputes a face match or a quiz score because it has the raw means to check. The signed-URL fetch was gated behind two unrelated calls, delaying the one thing the trainee is actually waiting on.** `TraineeLearnLessons.tsx`'s `selectLesson()` previously bundled `getLessonVideoUrl` into the same `Promise.all` as `getLessonProgress`/`getLessonTranslations` — `setVideoUrl` only fired once *all three* resolved, so a slow (or merely unlucky) progress/translations response delayed video start even though the video-url call itself might have already finished. The video-url fetch is now its own independent chain, setting state the moment *it* resolves regardless of the other two. Guarded against a real race: `videoFetchLessonIdRef` drops a superseded fetch's result if the trainee has already clicked a different lesson by the time it lands, rather than overwriting what's now on screen with a stale lesson's video.

**2. The loading state was actively misleading, not just absent.** `videoUrl === null` was the *only* state `SelfHostedVideoPlayer` had — used both while a fetch was genuinely in flight and for a lesson that truly has no video, rendering the identical "No video available for this lesson" message in both cases. A trainee clicking a real video lesson saw a message telling them there was no video, for however long the fetch took. Added a distinct `loading` prop, set by `selectLesson` for exactly the fetch's duration, rendering a spinner + "Loading video…" instead — same actual network time, but no longer indistinguishable from a dead end.

**3. No `preload` was set, and no buffering feedback existed once playback started.** `<video src={url} controls />` had no `preload` attribute, leaving how eagerly the browser starts pulling bytes to browser-default heuristics rather than an explicit choice; now `preload="auto"`. Added `onWaiting`/`onPlaying`/`onCanPlay` handlers showing a "Buffering…" overlay during a genuine mid-playback stall (a real network wait against B2), distinct from the pre-playback `loading` state above.

**4. Client-side signed-URL caching**, `packages/api-client`'s `getLessonVideoUrl`: every call previously minted a brand-new signed URL from scratch — a fresh Supabase DB lookup plus a fresh B2 presign — even for the exact same lesson requested seconds earlier (re-selecting a lesson, a remount). Now cached in-memory, keyed by lesson id, for 5 minutes (deliberately capped well under the server's real 1800s TTL, not the full window — the cache has no way to know if a trainer replaces the lesson's video mid-session, so a short cap keeps that staleness risk narrow while still catching the common case of quickly revisiting a lesson).

**What this does not fix, flagged rather than silently left alone**: the actual bytes-per-second a trainee gets is unchanged — B2 has no CDN/edge cache in front of it for video (unlike the PDF/slides path, which already goes through Supabase's own CDN — see DECISIONS.md #13/#20), and videos are uploaded and served completely unprocessed (whatever bitrate/resolution/codec/container the trainer's own file was, up to 2 GB, with zero compression or transcoding anywhere in the pipeline — DECISIONS.md #20's presigned-PUT design means the bytes never even pass through Express, so there's nowhere server-side this could currently happen). Both are real, substantially larger pieces of work — a CDN needs an external account/DNS decision, transcoding needs a new server-side pipeline and probably a new dependency (ffmpeg) — genuine scope/cost decisions for the user, not something to build unasked.

**Status**: Active. `apps/web/src/trainee/TraineeLearnLessons.tsx`, `apps/web/src/SelfHostedVideoPlayer.tsx`, `apps/web/src/YouTubeVideoPlayer.css` (new spinner/buffering-overlay styles, shared with `YouTubeVideoPlayer.tsx`'s empty state), `packages/api-client/src/index.ts`. `pnpm typecheck` (7/7), `pnpm --filter api test` (467/467, unaffected — frontend/api-client only), lint, build all clean. The new client-side cache was verified against the real shipped module (not a reimplementation), with a mocked `fetch` counting real invocations: a repeat call for the same lesson genuinely skips the network entirely and returns the identical URL, while a different lesson still fetches fresh — 6/6 assertions.

### 50. Optional CDN in front of B2 for lesson video — opt-in via `VIDEO_CDN_BASE_URL`, a deliberate trade of per-view expiry for cacheability, per direct user request following #49

**Decision**: #49 fixed what the client controls; the user asked to go further and add a CDN, since the remaining ceiling is B2 serving every single view fresh with no edge cache. A CDN can only cache a URL that stays the same across requests — the existing signed URL re-mints (and re-expires) on every call, which defeats caching entirely, since it's never the same URL twice. `GET /lessons/:id/video-url` now checks a new `getVideoCdnBaseUrl()` (`apps/api/src/b2Client.ts`) first: if `VIDEO_CDN_BASE_URL` is set, it returns a stable `${base}/${storage_path}` URL instead of signing one, skipping B2 entirely for the request (no `getB2Client()`/`getSignedUrl()` call at all). If unset — the default on every deployment until someone deliberately configures it — behavior is byte-for-byte what it was before this decision.

**The tradeoff, surfaced and confirmed before writing any code, not assumed**: a stable URL means the video is reachable at that one address for as long as the lesson exists, not re-checked against auth on every view the way a 30-minute signed URL effectively is. Presented this explicitly to the user as a real security-posture change, with the exact mechanism spelled out (Cloudflare can't cache a URL it never sees twice), and they chose the stable-URL approach explicitly — this is not a default anyone gets without opting in, and not a call made on the user's behalf. It mirrors a trust level this codebase already ships and has already accepted: DECISIONS.md #12's YouTube-hosted lesson video is exactly as "unlisted, not re-checked per view" as this — an unguessable UUID-based key is what keeps it from being enumerable, not per-request authorization. `requireAuth` still gates who can *ask* Express for the URL in the first place; what changes is that the answer, once given, works indefinitely rather than for 30 minutes.

**Implementation**: `getVideoCdnBaseUrl()` trims a trailing slash so the built URL never doubles one up. `storage_path` (`${lessonId}/${timestamp}-${originalFilename}`) is percent-encoded per path segment, not as a whole string, so a filename with spaces or other reserved characters still produces a valid URL without mangling the `/` structure. The YouTube-hosted branch (`storage_path === null`) is untouched — the CDN setting only ever applies to self-hosted video.

**What the user still needs to do, since this repo has no access to their Cloudflare/DNS/B2 dashboard**: point a domain they control (proxied, "orange cloud" on) at the B2 bucket's public S3 endpoint, ensure the bucket (or at least the video path) allows public read, then set `VIDEO_CDN_BASE_URL` to that domain. Documented in `apps/api/.env.example`. Nothing in this repo can complete that half — it's an external account/DNS action, not code.

**Status**: Active, code-complete, unit-tested (`lessonVideo.test.ts` +4 tests: stable URL returned and `getSignedUrl` never called when configured, percent-encoding, trailing-slash handling, YouTube lessons unaffected). Not yet live-verifiable end-to-end against a real CDN, since no Cloudflare/DNS setup exists yet on the user's side — confirmed the safe default is what's actually active right now (`VIDEO_CDN_BASE_URL` absent from the real `.env`), so this ships with zero behavior change until the user completes their half. `pnpm typecheck` (7/7), `pnpm --filter api test` (471/471), lint, build all clean.

### 57. Bulk CSV import for assessment questions — per direct user request, after seeding demo data by hand made the one-row-per-form cost obvious

**Decision**: typing each question through the single-question form (#53) doesn't scale past a handful of rows — a real module test with 20-30 questions meant 20-30 round trips. **CSV shape is a fixed column layout, not header-driven reordering**: `question_text, option_a..option_f (blank = unused), correct_option (matching letter), marks (optional, default 1)` — one column per possible option letter rather than a variable-width row, since the option count differs per question and a positional-from-the-end parse would be ambiguous. `AssessmentBuilder.tsx` parses the CSV entirely client-side (`parseQuestionCsv`), including a small quote-aware `splitCsvRow` — the existing trainee-CSV import (`AdminUserManager.tsx`) gets away with a plain `.split(",")` since names/emails/phones rarely contain commas, but question text routinely does, so that shortcut wasn't safe to reuse here. **How assignment works**: when approving a nomination, the admin can optionally pick a room from a dropdown (`PATCH /programmes/:id/nominations/:nominationId` accepts `hostel_room_id`/`hostel_notes`, only alongside `status: "approved"`). The room is validated *before* the approval is written, so a bad pick can't leave a nomination approved but half-assigned. Already-approved trainees can be given, moved to, or cleared from a room afterwards (`PUT`/`DELETE /programmes/:id/hostel-assignments/:traineeId`). Without that, anyone approved before this feature existed could never get a room, and a wrong pick could never be fixed. `unique (trainee_id, programme_id)` makes a re-assignment replace the row rather than stack up. Any number of trainees may share a room — this is integrity, not occupancy control. The one integrity rule that *is* enforced: a room must belong to a hostel of the programme's own institution, which is a cheap guard against picking another institute's hostel by mistake (`apps/api/src/hostelAssignment.ts`, shared by both write paths).

**Three decisions made with the user before building** (recommended options, all accepted):
- **Not shown on the public NFC profile.** That page needs no login, so a hostel and room number there would tell any stranger where the trainee sleeps — a real personal-safety and DPDP concern, and outside PRD §6.10's "skills, courses, certifications" scope for that page. The trainee sees it read-only on their own private profile instead (`trainee/HostelAssignmentCard.tsx`, rendered in `ProfileEditor.tsx` alongside `NfcProfileCard`). `publicProfile.ts` is untouched.
- **"Assign/change room" on already-approved nominations**, not only at approval time (see above).
- **No hand-typed `total_rooms` column.** The originally proposed `hostels.total_rooms` was dropped, because a manually entered count can silently disagree with the rooms actually recorded. The admin UI shows the real count of `hostel_rooms` rows instead.

**Deletion is refused, not cascaded**: `trainee_hostel_assignments.room_id` deliberately has no `on delete cascade`, so deleting a room — or a hostel, which cascades to its rooms — that still has trainees assigned fails on the FK. The API reports that as a 409. This is the same "refuse rather than silently destroy history" stance `institutions` takes toward their programmes.

### 65. In-app notification engine — the bell becomes real; push/email/SMS stay `TBD`

**Decision**: per direct user request ("set up a notification engine for assessments, content, lectures and other updates"), the placeholder bell in both web shells — whose own code comments said it "isn't wired to a real notification system yet", with an unconditional red dot — is now real. Scope was agreed with the user before building: **in-app only**. PRD §10 still lists the push provider (FCM/APNs) as `TBD`, and push, email, or SMS would each need a provider plus credentials. The engine is shaped so a future channel delivers these same rows rather than replacing them.

**Model** (migration `20260925000002_notifications.sql`): one `notifications` row per recipient per event, with a CHECK-constrained `type` and a jsonb `data` of the event's *parameters* — programme title, lesson title, room number, status. Rendered text is never stored. `apps/web/src/notifications/notificationContent.ts` builds the title, body, icon, and click target per locale from `type` + `data`, so the same row reads correctly in English or Hindi. Storing English text would have made Hindi users see English notifications.

**Triggers** (`apps/api/src/notificationService.ts`, called from the owning routes):
- **Trainee, own events**: their nomination was approved, waitlisted, or rejected; their certificate was issued; their hostel room was assigned or changed; an employer shortlisted them or updated that shortlist (PRD §8's "trainee notified" employer flow, never built until now).
- **Trainee, as a programme audience** (approved nominees only, the same roster definition attendance and the gradebook use): a new lesson; a new session; a new quiz or test.
- **Admins**: a trainee submitted a nomination.
- **Trainer**: they were assigned to a programme.

**Two noise rules**:
- A quiz or test announces itself when it gets its *first* question(s), not when an empty shell is created — an assessment with no questions can't be taken. Consequently, a bulk import of N questions produces one notification, not N.
- A session back-filled into the past, a record of a class already held, notifies no one.

**Best-effort, never blocking**: every notify helper swallows and logs its own failures, and routes call it as `void notifyX(...)` after their write has already succeeded — the same fire-and-forget posture as `embedJobBestEffort`. A notification can never turn a successful approval, lesson save, or certificate into an error.

**Delivery by polling, not realtime**: the bell (`NotificationBell.tsx`) polls a count-only endpoint (`GET /notifications/unread-count`) every 60s (`NOTIFICATION_POLL_INTERVAL_MS`), on window focus, and when the tab becomes visible. It loads the list only when opened. Supabase Realtime would need the browser to hold a direct Supabase connection, which CLAUDE.md rules out ("clients never call Supabase directly"), and a minute's latency is fine for this kind of news. A failed poll while offline is silently skipped.

**Security**: reads go through `req.supabase` under the new `notifications_select_own` RLS policy. There's no update policy, so marking read goes through `supabaseAdmin` but is always filtered by `recipient_id = req.user.id`. Marking someone else's id is a silent no-op (204), revealing nothing.

**Mobile header**: the bell was previously hidden below `md:` to stop the 375px header overflowing. Trainees are mostly on phones, so the bell is now shown at every width, and the header's *duplicate* theme toggle is hidden below `md:` instead. The accessibility strip at the top of the page keeps its own theme toggle at every width, so no function is lost and the header keeps the same control count.

**Status**: Active. Migration applied live by the user before implementation. Verified live end to end against the real database with the demo accounts — 14/14 checks:
- **Audience**: approved trainees receive lesson, session, and quiz notifications; a rejected trainee receives none; one trainee never receives another's employer update.
- **Noise rules**: a bulk 3-question import plus a 4th question later produced exactly one "new quiz" notification; a back-filled past session notified no one.
- **Approval with room**: approving a nomination with a room produced both the decision and the room notifications.
- **Read state**: a trainee cannot mark another trainee's notification read.

### 66. Gradebook export to a structured Excel workbook — `exceljs` added, generated server-side

### 68. AI Career Counsellor and skill-gap ranking moved from Gemini to Groq — one AI key for the whole platform (amends #27)

**Decision:** F12's career counsellor (tool-calling loop) and P1's "what to learn first" ranking now call Groq, like F7's chatbot already did since #35. All three share one helper, `apps/api/src/groqClient.ts`: a single fetch to Groq's OpenAI-compatible endpoint, with model, defaults and error handling in one place. The `@google/genai` dependency and `GEMINI_API_KEY` are gone.

**Why:** No Gemini key was configured anywhere, locally or on Render, so the counsellor returned 503 in every environment and the ranking silently never appeared. Groq was already provisioned and working for the chatbot. Running a second provider for the same capability doubled the setup burden for no benefit.

**How:**
- The counsellor keeps its six read-only tools, still always scoped to the server-verified caller, and its grounding rules. It moved from Gemini function calling to OpenAI-style `tools` / `tool_calls` / `role: "tool"` messages on `openai/gpt-oss-120b`.
- The ranking uses JSON mode (`response_format: json_object`) with the shape pinned in the prompt. The existing validation still drops any invented `skill_id`.

**Found live, not assumed:**
- **The 4-turn tool cap was too small.** gpt-oss requests one tool per turn, and a broad question ("what next, and am I job-ready?") needs about five lookups, so the cap is now 6.
- **The forced final answer could fail.** Once the cap was hit, the model could still attempt a tool call, which Groq rejects with a 400 ("Tool choice is none, but model called a tool"). The model is now told plainly that tools are finished, and a failure there returns the fallback answer instead of a 503.
- **Groq's free tier caps gpt-oss-120b at 8,000 tokens/minute**, which back-to-back counsellor questions exhaust. `groqChat` now retries once after a 429 when the `retry-after` wait is at most 10 s. The ranking moved to `openai/gpt-oss-20b`, which has its own per-model budget, so it doesn't compete with the chatbot and counsellor.
- **The certificates tool returned only the programme title**, so two course certificates from one programme looked like duplicates. It now includes the course title.

**Security:** `GROQ_API_KEY` is server-side only. The web app never calls Groq and must not be given the key: Vite inlines any referenced `VITE_*` variable into the public bundle.

### 69. Certificate redesigned to the approved Stitch design; every existing certificate re-rendered

**Decision:** The certificate PDF (`renderCertificatePdf` in `apps/api/src/certificateService.ts`) now implements the Stitch design in `stitch_coop_net_certificate_of_completion (1)/`:
- A double navy/orange border with rangoli-style corner tiles, and a faint "joined cooperative circles" watermark.
- **Header:** the NCCT letterhead with an emblem tile, and a COOP-NET / "सहकार उत्कर्ष • Sahakar Utkarsh" brand mark.
- **Body:** a letter-spaced Cinzel title with an orange accent, a Playfair recipient name, then the course and programme.
- **Result badge:** a pill with the marks, or just "COURSE COMPLETED" when the course had no graded tests.
- **Footer:** a three-column verification / certificate ID / signatory row and a disclaimer strip.

**How the design maps to the PDF:**
- It is drawn in PDFKit, as before; there is no HTML-to-PDF step. The design's CSS px values are converted with one factor (`px()` = ×0.75, 1123×794 px → 842×595 pt), so the code can be checked against the reference.
- **Fonts:** two new OFL fonts in `apps/api/assets/fonts/`:
  - JetBrains Mono SemiBold, for the certificate ID and URL.
  - Noto Sans Devanagari Medium: Roboto has no Devanagari, and PDFKit's fontkit shaping renders conjuncts such as "र्ष" correctly. Checked by rasterising the PDF.
- **Long values:** long names shrink to fit one line (34 → 24 px) before wrapping; long course titles drop a size; the institution name and verification URL shrink, then truncate. Tests pin the graded, ungraded and very-long variants to one page with all five fonts embedded.
- **Removed from the old design:** the "NCCT ★ SEAL ★ OFFICIAL" stamp and the "Government of India" footnote, consistent with #67 (no official-looking seals or claims the platform can't back).
- **Issue dates:** now formatted in IST.

**Existing certificates:** `rerenderCertificate()` plus `pnpm --filter api certificates:regenerate` re-render every issued certificate without changing what it certifies. The code, issue date, frozen marks (#53) and QR target stay the same; current names are used.
- **New file, not an overwrite.** Each new PDF goes to a fresh `CODE-<version>.pdf` path and the row is repointed. Public Storage URLs are CDN-cached, so an overwrite could keep serving the old design for up to an hour, and the previous file stays as a backup.
- **Localhost guard.** The script refuses a localhost `PUBLIC_WEB_URL`, since that value is what every QR code encodes.
- **Result:** run on 2026-09-26, all 5 live certificates were re-rendered, 0 failed. Verified through the real `GET /certificates/mine` and the public verification endpoint.
