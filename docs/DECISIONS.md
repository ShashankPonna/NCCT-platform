# Architecture Decisions

Lightweight decision log — why key choices were made, so future changes are deliberate reversals rather than silent drift. Add a new entry (don't edit past ones) when a decision changes; mark the old one Superseded.

---

### 1. One backend serves both web and mobile

**Decision**: Single Node/Express REST API consumed by both the React web app and the React Native app; no separate mobile-specific API.
**Why**: A REST API doesn't need to know whether its caller is a browser or a phone. Duplicating it would double the bug surface and let web/mobile drift out of sync on business logic.
**Status**: Active.

### 2. One shared Supabase database

**Decision**: Single Supabase Postgres instance for both clients, accessed only through Express.
**Why**: Follows directly from Decision 1 — a shared backend implies a shared data source. No product reason for web-only or mobile-only data.
**Status**: Active.

### 3. Separate UI codebases (React web + React Native), not React Native Web

**Decision**: Web and mobile have independent UI code; only the logic layer (`packages/*`) is shared.
**Why**: The two surfaces have genuinely different UI shapes — dashboard/table-heavy admin+employer screens on web vs. camera/NFC/offline-native trainee screens on mobile. Forcing one UI codebase via RN-Web would fight both use cases.
**Status**: Superseded by #19 — the "camera/NFC-native trainee screens" premise turned out to be wrong (see #19); the React-Native-vs-web split doesn't apply once mobile no longer needs native camera/NFC.

### 4. Clients never call Supabase directly

**Decision**: All data access goes through Express; Supabase service credentials are server-side only.
**Why**: Centralizes auth checks, face-recognition matching, PDF generation, and chatbot orchestration in one place instead of duplicating business rules in RLS policies and two clients.
**Status**: Active.

### 5. Face recognition: `@vladmandic/human` as default, InsightFace `buffalo_l` as swap-in alternative

**Decision**: Use the JS-native `@vladmandic/human` library (runs in Node via tfjs-node) for face detection/embedding extraction in the Express face-rec service. If accuracy proves insufficient, swap the extraction step to InsightFace's `buffalo_l` ONNX models (mirrored on Hugging Face) via `onnxruntime-node` — the storage/comparison logic downstream (pgvector cosine similarity) stays the same either way.
**Why**: Human integrates fastest given an all-JS/TS stack and runs on both Node and React Native. `buffalo_l` is higher accuracy but adds ONNX-inference wiring; kept as a documented fallback rather than the default to avoid premature complexity.
**Status**: Amended by #16 — the library choice (`@vladmandic/human`) is still active, but *where extraction runs* changed from "the Express service" to "the browser client." **Dimension correction**: the two options in this decision do **not** produce the same descriptor size, contrary to what the initial schema assumed — Human's faceres output is **1024-d**, InsightFace `buffalo_l` is 512-d (measured, not assumed; see migration `20260901000011`). Swapping to `buffalo_l` later therefore means recreating `face_embeddings.embedding` at 512 and re-enrolling every trainee, not just changing the extraction call. Revisit after real-world accuracy testing.

### 6. NFC: static NDEF URI tag, not custom in-app read/write

**Decision**: NFC cards encode a URL to the trainee's public profile page (reusing the certificate-verification page pattern), written once at issuance. No custom NFC read/write logic is built into the apps for MVP.
**Why**: NFC tags hold too little storage (144–888 bytes on common tags) for a full profile — a URL is the only sane payload. Tapping a tag with a native OS NFC reader opens the URL on both Android and iOS with no app installed, sidestepping Web NFC's Chrome-Android-only support and iOS's tag-write restrictions.
**Status**: Active.

### 7. Offline sync: timestamp/last-write-wins, not CRDT/OT

**Decision**: Mobile queues offline writes locally and replays them against the same Express endpoints on reconnect; conflicts resolved by last-write-wins on client timestamp.
**Why**: The data involved (progress events, quiz results, attendance) is mostly append-only, not collaboratively edited — a full CRDT/operational-transform sync engine would be solving a problem this data shape doesn't have.
**Status**: Active. Fairness edge cases near deadlines are a known open question (see PRD §14).

### 8. Monorepo: pnpm workspaces, not Turborepo/Nx

**Decision**: Use plain pnpm workspaces to let `apps/*` import from `packages/*` locally.
**Why**: Sufficient for the project's current size; Turborepo/Nx's build-caching benefits aren't needed until build times or team size actually justify the extra tooling.
**Status**: Active. Revisit if build/CI times become a real pain point.

### 9. Express uses per-user Supabase clients for user-owned data, service-role only for privileged operations

**Decision**: The auth middleware builds a request-scoped Supabase client using the caller's own JWT (so Postgres RLS evaluates as that user) for routes acting on a user's own data. A separate service-role client (`supabaseAdmin`) is used only where the operation is legitimately cross-user or privileged (e.g., admin approving a nomination, issuing a certificate, writing a face embedding after consent).
**Why**: `CLAUDE.md`'s security rule states Express role middleware and Supabase RLS are "defense in depth, not either/or." That's only true if Express doesn't call Supabase exclusively with the all-powerful service-role key (which bypasses RLS entirely) — otherwise RLS is enabled but inert. Splitting the client this way makes RLS a real second layer instead of a checkbox.
**Status**: Active. Individual routes still decide per-case which client to use; there's no automatic rule beyond "user's own data → user-scoped client."

### 10. Vitest (not Jest) for `apps/api` tests

**Decision**: Use Vitest + Supertest for API tests instead of the originally proposed Jest + Supertest.
**Why**: `apps/api` is ESM (`"type": "module"`) with `NodeNext` module resolution. Jest's ESM support requires extra transform/config friction (`ts-jest` ESM preset, `extensionsToTreatAsEsm`, moduleNameMapper for `.js` specifiers) that Vitest avoids natively — it was faster to get a real, working test running than to fight Jest's ESM setup. `CLAUDE.md`'s testing section explicitly said "confirm before first test is written, then remove the caveat"; this is that confirmation.
**Status**: Active for `apps/api`. Web is a natural fit for Vitest too (same Vite tooling) if/when its test setup is confirmed. Mobile stays Jest (`jest-expo` preset) since that's the RN/Expo ecosystem standard, not Vitest.

### 11. `apps/api` splits `app.ts` (Express app, exported) from `index.ts` (thin `listen()` entrypoint)

**Decision**: `apps/api/src/app.ts` builds and exports the configured Express app; `apps/api/src/index.ts` only imports it and calls `.listen()`.
**Why**: Supertest needs an importable `app` object to test against directly, without binding a real port. This is the standard pattern for testable Express apps, not a speculative abstraction — it was introduced exactly when the first test needed it, per `CLAUDE.md`'s "minimal change that satisfies the requirement."
**Status**: Active. Every future route file goes in `apps/api/src/routes/` and is mounted onto `app` in `app.ts`.

### 12. Lesson video hosted as YouTube unlisted videos (prototype), PDFs stay on Supabase Storage

**Decision**: For the SIH prototype, `lessons.content_type = 'video'` rows store only an 11-character `video_id` (validated by regex both client-side via zod and DB-side via a `CHECK` constraint) — never a full URL, never the video file itself. The web app embeds it with the official `https://www.youtube.com/embed/{video_id}` iframe player via a reusable `YouTubeVideoPlayer` component (`apps/web/src/YouTubeVideoPlayer.tsx`). Non-video lesson content (PDF/slides) continues to use `lessons.storage_path` against Supabase Storage, as already implied by the initial schema — this decision only concerns the video path.
**Why**: Building real private video delivery (signed URLs, a CDN, DRM) is out of scope for a hackathon prototype and would be premature infrastructure. YouTube's iframe player gets a working, embeddable, responsive video player with zero backend video-serving code. "Unlisted" only means the video is unlisted on YouTube itself — it is **not** access-controlled by our app's auth; anyone with the link (leaked or guessed) can view it. This must not be described as private/secure content, and it is not suitable for anything requiring real confidentiality.
**Status**: Active for the prototype. **Migration note**: because only an opaque `video_id`/key is stored on the lesson row (never the file), swapping this for private object storage + CDN/signed URLs later only changes how that key is resolved into a playable URL — it does not require changing the `lessons` table shape or the LMS content hierarchy.

### 13. PDF/slides lessons: upload through Express, read via short-lived signed URLs

**Decision**: The `lesson-content` Supabase Storage bucket is **private** (`public: false`). Uploads go `client → Express (multipart, `multer`) → supabaseAdmin.storage.upload()`; the client never gets direct Storage write access, per ARCHITECTURE.md §8. Reads work differently: Express checks the caller is authenticated (any role can read; RLS-equivalent same as lesson content generally) and then calls `supabaseAdmin.storage.createSignedUrl()` with a 60-second TTL, returning that URL to the client — the actual file bytes then flow straight from Supabase's CDN to the browser, not proxied through Express.
**Why**: Proxying PDF bytes through Express would work but wastes Express's bandwidth/memory for no security benefit once the authorization decision (does this caller get a URL at all) has already been made — the same reasoning already applied to lesson video in Decision #12's "don't proxy the video" note. A private bucket + short-lived signed URLs keeps the actual authorization check server-side (a leaked signed URL only works for 60 seconds) while still letting large files be served efficiently. This is a read-only exception to "clients never call Supabase directly" — the client calls Supabase's CDN with a token Express minted, not Supabase's API with its own credentials, and it can never do so without Express's say-so first.
**Status**: Active.

### 14. Interactive lessons: `lessons.interactive_config` as jsonb, one exercise type (`matching`) to start

**Decision**: A `content_type: 'interactive'` lesson stores its exercise definition in a new `lessons.interactive_config` jsonb column rather than a normalized table (e.g. `interactive_exercises` + `interactive_exercise_items`). Only one exercise type exists so far — `matching` (term ↔ definition pairs, rendered client-side as a tap-to-pair exercise, graded client-side since there's no "submission" concept for it, unlike a quiz). The zod schema (`interactiveConfigSchema`) is a discriminated union on `type`, currently with one member, so adding a second exercise type is a compile-time-visible change (every `switch`/consumer has to handle it), not a silent JSON shape drift.
**Why**: PRD only requires "at least one genuinely interactive element," not a general-purpose exercise-authoring system — building normalized tables for a still-hypothetical second/third exercise type would be exactly the kind of premature abstraction `CLAUDE.md` says to avoid. jsonb keeps the DB shape stable while the exercise-type roster is still unknown; if a second type needs its own indexed queries later (not just "fetch by lesson"), that's the trigger to normalize, not before.
**Status**: Active. Revisit if a second interactive exercise type needs querying/reporting beyond "attached to this lesson."

### 15. Assessment questions: no RLS read policy at all; correct answers stripped in Express, not in the database

**Decision**: `assessment_questions` is the one content table in this codebase with **no** authenticated-read RLS policy — every other F3/F4 table (`courses`, `modules`, `lessons`, `content_translations`, `assessments`) got one. All reads of `assessment_questions` go through `supabaseAdmin` in Express: the admin/trainer authoring routes (`GET /assessments/:id/questions`) return the full row including `correct_option_id`; the trainee-facing route (`GET /assessments/:id/take`) builds a new object per question naming only the safe fields (`id`, `assessment_id`, `question_text`, `options`, `position`) — `correct_option_id` is never spread into the response. Grading (`POST /assessments/:id/attempts`) also reads the table via `supabaseAdmin` to compare submitted answers against `correct_option_id` server-side, then inserts the graded `assessment_attempts` row via `supabaseAdmin` too, rather than `req.supabase` — unlike every other own-row insert in this codebase (nominations, lesson_progress), which do use the caller's own RLS-scoped client.
**Why**: Postgres RLS is row-level, not column-level. A policy letting a trainee `SELECT` their own module's questions would have no way to hide just the `correct_option_id` column while allowing the rest — the policy would have to leak the answer key to give any read access at all. Since the correct answer must never reach the browser before grading, the only sound options were per-column Postgres `GRANT`s (real but heavier machinery, and this table has no other consumer that would benefit from it) or keeping this table entirely behind the service-role client and filtering in application code, where the "strip this field" logic is a one-line, easily-reviewed operation. The attempt insert uses `supabaseAdmin` for a related reason: correct grading requires reading `correct_option_id` in the same request handler regardless, so there was no security benefit left to gate the insert through a separate RLS-scoped client — `trainee_id` is still always taken from `req.user`, never the request body, so a trainee still can't submit as anyone else.
**Status**: Active. This is a deliberate, narrow exception — every other table added for F3/F4 does get an authenticated-read RLS policy per the established default (DATABASE.md).

### 16. Face embedding extraction runs in the browser (`apps/web`), not the Express service — amending #5

**Decision**: `@vladmandic/human` still does face detection/embedding extraction (the library choice in #5 is unchanged), but that extraction now runs client-side in `apps/web` (browser, WebGL backend) rather than server-side in Express as #5 originally described. A trainee's browser captures a webcam frame, runs Human locally, and sends only the resulting 512-number embedding array to Express — never a raw image. Express's face-rec responsibilities become: verify recorded consent, store the embedding (`face_embeddings`, own-row RLS), and — critically — always **recompute** the match server-side (cosine similarity against the trainee's own stored embedding(s)) rather than trusting any client-reported match result, per `CLAUDE.md`'s "never trust a client-reported ... face-match result" rule. The client only ever supplies the raw embedding, never a match score or a pass/fail verdict.
**Why**: Tried the server-side path first and it doesn't work on a stock Windows dev machine. `@vladmandic/human`'s Node build has two options: (1) `@tensorflow/tfjs-node` (native bindings) — a real install attempt failed outright (`npm install @tensorflow/tfjs-node`) because no prebuilt binary exists for this Node/ABI combination and the fallback native compile needs Visual Studio's C++ build tools, which aren't installed and aren't something to demand of every dev machine for a prototype; (2) the WASM Node build (`@vladmandic/human/dist/human.node-wasm.js`, no native compilation) — this **does** install and load cleanly, but a real end-to-end test (a photo with multiple clearly visible faces, run through blazeface detection) returned zero face detections while the same pipeline's body detector (movenet) correctly found a person in the same frame — a reproducible wasm-backend-specific failure in the face detector, not a config mistake (confirmed by lowering `minConfidence` to 0.05 and still getting zero results). Since Human is fundamentally built, tested, and documented as a browser-first library (WebGL backend), and the trainee's device already needs camera access for this feature regardless, running extraction in `apps/web` sidesteps both failure modes entirely and is arguably better for the DPDP Act's data-minimization principle besides — the raw camera image never has to leave the trainee's device at all, only the derived embedding does.
**Status**: Active. If mobile (`apps/mobile`) later needs face check-in, the same "extract on-device" approach applies there too (Human also runs in React Native), not a return to server-side extraction. Revisit if a future accuracy/consistency problem specifically requires centralizing extraction.

### 17. Chatbot embeddings: a local model (`Xenova/all-MiniLM-L6-v2`), not a hosted embedding API

**Decision**: F7's RAG retrieval generates embeddings **locally inside the Express service** using `@huggingface/transformers` (Transformers.js) with `Xenova/all-MiniLM-L6-v2` — 384 dimensions, mean-pooled and L2-normalized. This resolves the long-standing open question that `chatbot_corpus_chunks.embedding vector(1536)` was a placeholder for; the F7 migration recreates that column as `vector(384)`. Answer *generation* still uses the Claude API (`claude-opus-5`) per PRD §10 — only the embedding half is local. Retrieval itself is a Postgres function (`match_corpus_chunks`) using pgvector's cosine operator, called from Express via `supabase.rpc()`, because PostgREST's query builder cannot express `<=>`.
**Why**: Anthropic has no first-party embeddings API (their documented recommendation is Voyage AI), so "use Claude for embeddings too" was never an option — the real choice was between a second paid vendor (Voyage/OpenAI) and a local model. Local wins here on four counts: (1) **one key instead of two** — F7 already requires an `ANTHROPIC_API_KEY` for generation; a hosted embedding provider would add a second account, key, and bill to a project that has no committed API budget; (2) **no per-query cost or rate limit** on the highest-frequency operation in the feature (every question embeds, and every corpus chunk embeds once); (3) **it works offline once cached**, which is directionally right for a platform whose stated non-functional requirement (PRD §7) is low-bandwidth rural usability; (4) **verified quality and installability before committing** — a spike embedded a representative domain query and scored 0.87 cosine against a relevant sentence vs 0.02 against an unrelated one, then live retrieval against the real database ranked a dairy-programme chunk first at 0.731 for a dairy question, with the next-nearest at 0.404. Install was checked explicitly against the trap that burned F5: the package installs cleanly on this Windows machine and runs on the WASM backend without `onnxruntime-node`'s native binaries (their build scripts are declared off in `pnpm-workspace.yaml`), so there is no repeat of DECISIONS.md #16's native-compilation dead end.
**Status**: Active. **Migration note**: the swap cost to a hosted provider later is small and well-contained — `embedText()` in `apps/api/src/chatbotService.ts` is the only place embeddings are produced, so switching means changing that one function, changing `EMBEDDING_DIMENSIONS`/`EMBEDDING_MODEL` in `packages/constants`, and running a migration that recreates the column and the RPC signature at the new dimension (plus re-embedding the corpus, which is cheap at this size). Retrieval SQL, route shapes, and the answer-generation path are all dimension-agnostic and would not change. Worth revisiting if retrieval quality proves insufficient on a real corpus — MiniLM is a small model, and Voyage's domain models would be the first upgrade to try.

### 18. Self-hosted lesson video via Cloudflare R2 (presigned URLs) — supersedes #12's YouTube-only approach

**Decision**: Course video lessons can now carry either a YouTube `video_id` (the original #12 approach, unchanged for existing content) or an R2 `storage_path`, mutually exclusive in practice on the same `lessons` row — no schema migration needed since `storage_path` already existed, shared with the PDF/slides upload path. Video bytes never transit Express: `POST /lessons/:id/video-upload-url` (admin/trainer) mints a presigned S3-compatible PUT URL against R2 via `@aws-sdk/client-s3`/`@aws-sdk/s3-request-presigner`, the browser uploads straight to R2 with it, then the caller attaches the resulting key with the existing `PATCH /lessons/:id`. Playback mirrors this with a presigned GET (`GET /lessons/:id/video-url`), same pattern as #13's PDF/slides signed reads.
**Why**: YouTube hosting (#12) requires content to already be public/unlisted on YouTube, which doesn't fit institution-authored training material that may not belong on a public video platform at all. R2 was chosen over Supabase Storage (already used for PDFs/slides, #13) specifically because video files are large — buffering a multi-hundred-MB upload through Express's memory the way the 25MB PDF path does (`multer`, in-memory) doesn't scale — and R2 has **zero egress fees**, which matters for a platform whose content gets streamed repeatedly by trainees on limited connections (PRD §7). This is the same narrow exception to "clients never call storage directly" that #13 already established: the client only ever talks to R2 with a token Express minted, never with its own credentials, and cannot get one without Express's say-so first.
**Cost tradeoff, stated plainly**: R2's free tier (10 GB storage, 1M Class A ops/month, 10M Class B ops/month, $0 egress always) is generous for a prototype, but unlike Backblaze B2 — the other candidate considered — **R2 has no hard spending cap**. Cloudflare only offers non-blocking budget-alert emails past a configured threshold; nothing stops usage automatically. B2 has a real, enforced daily cap. R2 was chosen anyway because free egress matters more here than a hard cap does at this scale, but this is a real operational gap someone should set a budget alert for (see manual setup steps given to the user), not an oversight.
**Status**: Superseded by #20 — moved from R2 to Backblaze B2 before any real credentials were ever configured, so nothing in production depended on R2 specifically. The presigned-URL architecture this entry describes is unchanged; only the storage provider changed.

### 19. Mobile app rebuilt on Capacitor, not React Native/Expo — supersedes #3's rationale for `apps/mobile`

**Decision**: `apps/mobile` is now a Vite + React web app (the same stack as `apps/web`, not React-Native-Web — see below) wrapped in a native Android shell via Capacitor (`@capacitor/core`, `@capacitor/android`, `@capacitor/cli`). The Expo/React Native starter that previously occupied `apps/mobile` (`App.tsx`, `app.json`, `expo`/`react-native` dependencies, `eslint-config-expo`) is removed entirely, not kept alongside the new setup. `capacitor.config.ts` points `webDir` at the Vite build output; `npx cap sync android` copies that build into the native `android/` project (committed to version control, per Capacitor's convention — it isn't fully regenerable from config the way Expo's managed `ios`/`android` folders were).
**Why**: #3's justification for a separate React Native codebase was specifically "camera/NFC/offline-native trainee screens on mobile." That premise turned out to be false: this project's face-recognition attendance uses an ESP32-CAM and its NFC card reads use a dedicated hardware reader, both integrated on the **web** side (an institution's front-desk/kiosk terminal), never the trainee's own phone. Once camera and NFC access are off the table, the only things `apps/mobile` actually needs per PRD §6.9 are: download course videos/quizzes for offline use, take quizzes offline, queue progress/attendance writes locally, and sync on reconnect (`last-write-wins`, unchanged from #7). None of that requires native UI — a WebView-wrapped web app can do all of it via Capacitor's `@capacitor/filesystem` (downloads) and a SQLite plugin (offline queue, not yet added — see Missing below), and doing so lets `apps/mobile` reuse `apps/web/src/trainee/*`'s screens (already built, already backend-verified) instead of rebuilding an entire second UI from scratch in React Native, which is what made F9 the flagged highest-complexity remaining MVP module in the first place. This is a direct, deliberate reversal, not silent drift — recorded here per this file's own rule, and discussed with the user before building (mobile architecture was raised, reasoned through, and approved before any code changed).
**Not React-Native-Web**: this doesn't reopen #3's Web/RN-Web question — `apps/web` (admin/employer dashboards) and `apps/mobile` (trainee-only, Capacitor-wrapped) remain genuinely different apps for genuinely different audiences; they just now share the same underlying framework (Vite/React) and, going forward, are expected to increasingly share actual trainee UI code, not only the `packages/*` logic layer #3 originally scoped the sharing to.
**Status**: Active, but scaffold-only so far. **Built**: the Capacitor + Vite shell itself, real Supabase Auth sign-in against the live API (`GET /api/profile`), a minimal authenticated home screen, and a generated, buildable `android/` native project (verified: `tsc -b` and `vite build` both clean; `npx cap add android` succeeded). **Missing** (tracked in `docs/IMPLEMENTATION.md`'s F9 entry, not silently assumed done): the actual trainee screens (lessons, nominations, certificates, jobs) haven't been ported from `apps/web/src/trainee/*` yet; no offline storage is wired up (`@capacitor/filesystem` and a SQLite plugin aren't installed yet — deliberately not added until the feature that uses them is actually built, per this repo's "don't add a dependency ahead of the code that needs it" convention); no forgot-password flow on mobile yet (needs Capacitor deep-linking, noted in `LoginForm.tsx`); and building a real APK needs the Android SDK, which isn't present in this dev environment — `npx cap add android` succeeded (that step doesn't require the SDK), but `./gradlew assembleDebug` does, so producing an actual `.apk` is a manual step for whoever has Android Studio installed.

### 20. Lesson video storage moved from Cloudflare R2 to Backblaze B2 — supersedes #18's provider choice

**Decision**: Same presigned-URL architecture #18 already built (`POST /lessons/:id/video-upload-url` mints a presigned PUT, `GET /lessons/:id/video-url` mints a presigned GET, both via the AWS S3 SDK against an S3-compatible endpoint) — only the provider underneath changed, from Cloudflare R2 to Backblaze B2. `apps/api/src/r2Client.ts` is replaced by `apps/api/src/b2Client.ts`; env vars changed from `R2_ACCOUNT_ID`/`R2_ACCESS_KEY_ID`/`R2_SECRET_ACCESS_KEY`/`R2_BUCKET_NAME` to `B2_ENDPOINT`/`B2_KEY_ID`/`B2_APPLICATION_KEY`/`B2_BUCKET_NAME`. The api-client function that used to be named `uploadLessonVideoToR2` is renamed `uploadLessonVideoFile` — provider-neutral, since nothing about the client side is actually R2- or B2-specific, only the signed URL it's handed is.
**Why**: #18 already documented R2's real gap honestly — no hard spending cap, only non-blocking budget-alert emails — and named B2 as the alternative that does have one. Since no real R2 credentials were ever configured (the feature shipped as scaffold-only, per #18's own status), switching before going live cost nothing and closes that gap for real rather than living with it. B2's free tier (10 GB storage, 2500 Class A + 2500 Class B "download" transactions/day free, egress free up to 3x stored data monthly) is comparable to R2's for this project's scale, and its S3-compatible API means the swap was almost entirely a rename, not a rewrite — the presigned-URL flow, the "video bytes never transit Express" reasoning, and the client upload/playback shape from #18 all carry over unchanged.
**Status**: Active, and **live-verified end-to-end against the real bucket**: real credentials were supplied, a real file was PUT to a presigned URL, attached to a real lesson, read back through a presigned GET, and the fetched bytes were byte-for-byte confirmed to match the upload — not just confirmed by code review or mocks. `B2_ENDPOINT`/`B2_KEY_ID`/`B2_APPLICATION_KEY`/`B2_BUCKET_NAME` are set in `apps/api/.env` (documented in `.env.example`); without them, video routes return 503, every other route is unaffected. `B2_ENDPOINT` is copied verbatim from the bucket's page in the B2 dashboard (`b2Client.ts` extracts the region from it for SigV4 signing rather than asking for a second, driftable env var). The trainee-playback gap #18 flagged is closed: `TraineeLearnLessons.tsx` calls `GET /lessons/:id/video-url` when a video lesson has no `video_id`, and `SelfHostedVideoPlayer.tsx` renders the result; `AdminCourseManager.tsx` has an actual "Upload Video File" control (progress bar, presigned PUT, then attaches the key via `PATCH /lessons/:id`). **One real gap found during live verification**: `updateLessonSchema.storage_path` is `z.string().optional()`, not `.nullable()` — there is no way to explicitly clear a lesson's `storage_path` via the API; an empty string works as a practical stand-in (every consumer treats it as falsy, identical to unset) but isn't a designed "detach" affordance. Not fixed yet — noted for whenever a "remove video" admin control is built. A small leftover test object (~20 bytes) remains in the live bucket from this verification; there is no delete route yet to clean it up automatically.

### 21. Face-recognition attendance moves to ESP32-CAM-fed kiosk capture — amends #5/#16, narrows F5's trainee-facing scope

**Decision**: Trainee self-service face check-in via the browser's own camera (`FaceCapture.tsx`, `getUserMedia` + client-side `@vladmandic/human` extraction, per #16) is superseded as the production check-in path. Face-recognition attendance instead runs from an ESP32-CAM (external hardware) feeding frames into the web app at an institution-operated kiosk/front-desk terminal — trainees do not use their own device's camera for face check-in at all, on either web or mobile.
**Why**: Confirmed directly with the user — the real hardware plan for this project pairs an ESP32-CAM (attendance) and a dedicated NFC reader (profile lookup) with the web client, both operated at an institution's kiosk, not on a trainee's personal device. `FaceCapture.tsx`'s current `getUserMedia`-based flow was built earlier in this project before that hardware context was known to whoever was building it at the time, and worked correctly as designed then — it just isn't the intended production path once the real hardware is accounted for.
**Practical effect, not yet built**: (1) `TraineeAttendance.tsx`'s embedded `FaceCapture` should eventually be removed from the trainee's own portal — trainee self-service attendance stays QR-code check-in only, already the other supported path. (2) A new kiosk-facing face check-in flow needs building, most likely in `AttendanceManager.tsx` (admin/trainer-operated) rather than trainee-facing: the ESP32-CAM most plausibly serves its own MJPEG/HTTP video stream on the local network, which a kiosk browser page would point a `<video>`/`<img>` element at and canvas-capture frames from — reusing the same client-side `@vladmandic/human` extraction pipeline #16 already validated, just fed a different frame source (an ESP32-CAM stream instead of `getUserMedia`), keeping #16's core reasoning intact (extraction stays client-side; Express only ever recomputes/verifies the match server-side, never trusts a client-reported result). The exact wire protocol (does the ESP32-CAM serve MJPEG directly, or need a small companion relay) is still open — needs the actual hardware or its documentation to pin down. (3) `apps/mobile`'s Attendance screen (F9) needs no camera UI at all as a result — QR-only, which simplifies that port rather than complicating it.
**Status**: Partially built. `FaceCapture`/`FaceEnrollment` are no longer rendered by `TraineeAttendance.tsx` (removed as part of #23) — trainee self-service attendance is QR-only now, as decided. The two components themselves are deliberately left on disk, unreferenced, as the extraction pipeline the future kiosk-facing flow is meant to reuse — not deleted, just currently dead code (confirmed harmless: an unimported module costs nothing in the Vite build, verified by the bundle-size drop recorded in #23). **Still not built**: the actual kiosk-facing ESP32-CAM flow in `AttendanceManager.tsx` — that's the real remaining work this entry describes.

### 22. Mobile app wraps the whole web app (all roles), not a trainee-only build — amends #19

**Decision**: `apps/mobile` is now a thin Capacitor shell with no `src/` of its own — `capacitor.config.ts`'s `webDir` points at `apps/web`'s own build output (`../web/dist`), and `App.tsx`'s existing role branching (already the mechanism that decides admin/trainer/employer vs. trainee UI on web) is what decides what a signed-in user sees on mobile too. `apps/mobile/package.json` keeps only the `@capacitor/*` tooling and two scripts — `sync` and `android` — that build `apps/web` first, then `cap sync`/`cap open`. The standalone scaffold #19 originally built (its own `LoginForm`/`Home`/`useSession`/`supabaseClient`/`index.css`) is deleted, not kept alongside this.
**Why**: Discussed directly with the user, who preferred one app for every role over a trainee-only one — and on reconsideration, the strongest objection to that (shipping the admin UI's code to every install) doesn't actually hold: `apps/web` is already a public site, so that code is already served to anyone who loads it; Capacitor-wrapping it exposes nothing new. What's left is only mobile-screen ergonomics for the dashboard-heavy Admin/Employer views, which is a CSS/responsiveness concern to address incrementally, not an architectural reason to fork the codebase. Against that, the standalone-scaffold approach had a real, ongoing cost: every trainee screen and its dependencies (`ProfileEditor`, `QuizTaker`, `MatchingExercise`, video players, etc.) would need copying into `apps/mobile/src` and hand-kept in sync with `apps/web` forever. Wrapping the real build has none of that cost — one codebase, one build, zero drift.
**Real consequence, found while implementing this, not assumed**: wrapping `apps/web`'s actual build means `apps/mobile` now hard-depends on `apps/web` compiling successfully — `pnpm --filter web build` runs `tsc -b` first, and at the time of this change that failed on 21 pre-existing errors left by the in-flight Stitch admin redesign (documented, not new). Under the old standalone-scaffold architecture this coupling didn't exist; mobile could be built independently of web's state. All 21 were fixed in this same round as a prerequisite, each with a real fix rather than a compiler-satisfying cast (an institution's separate state/district inputs now combine into the one `location` field the backend actually has, since there's no separate columns; the bulk-import summary now reads the real `rows: BulkImportRow[]` array instead of treating count fields as arrays; the timetable-session form gained an actual location input where one had never existed; lesson translations gained an actual body textarea; `duration_minutes` — never a real backend field — was removed from both the lesson form and the display rather than added to the schema, since nothing asked for it; two dead `"policy"` branches in the chatbot corpus UI were removed, since only `"programme"`/`"faq"` are real source types). Full detail in `docs/IMPLEMENTATION.md`'s change log for this date.
**Status**: Active, and verified working end-to-end: `pnpm --filter web build` (`tsc -b` + `vite build`) succeeds clean, `pnpm --filter mobile sync` runs that build and `npx cap sync`, and the resulting `android/app/src/main/assets/public/` was confirmed to contain the real web app's actual bundle and assets — not a stub. The `@vladmandic/human` bundle-size cost this entry originally flagged is resolved — see #23, which removed `FaceCapture` from the trainee flow and confirmed via the actual build output that the ~1.5MB/409KB-gzipped chunk is now gone entirely. **Not yet built**: mobile-specific responsive polish for the Admin/Employer screens.

### 23. Offline mode (F9's real remaining scope) — storage via Preferences + Filesystem, not SQLite

**Decision**: F9's offline layer lives in `apps/web/src/offline/` (not `apps/mobile` — that package has no `src/` per #22), consumed by the trainee-facing screens that need it. Four pieces: `storage.ts` persists a write-queue and a downloaded-lesson manifest as JSON via `@capacitor/preferences` (not `@capacitor-community/sqlite`); `network.ts` exposes `useOnlineStatus()` via `@capacitor/network`; `downloadManager.ts` downloads a self-hosted video lesson's file to `@capacitor/filesystem`'s `Directory.Data` (video only, not PDF/slides — see Why); `syncManager.ts` provides `enqueueWrite()` and `useAutoSync()`, which flushes the queue in order against the same real endpoints (`updateLessonProgress`, `submitAssessmentAttempt`, `checkInWithQr`) the moment the app comes back online, stopping at the first failure rather than skipping past it so ordering is never violated.
**Why Preferences over SQLite**: the actual data here — a queue of pending writes, a small manifest of downloaded lesson IDs — is a JSON array, not a relational dataset that benefits from SQL querying. `@capacitor-community/sqlite`'s web implementation needs a bundled WASM binary and a `jeep-sqlite` custom element just to run in a browser at all; Preferences has a real native and web implementation with none of that setup. CLAUDE.md is explicit about not reaching for more machinery than the data shape actually calls for, and a write-queue of at most a few dozen small JSON objects is comfortably within Preferences' intended range.
**Why video-only downloads, not PDF/slides too**: PRD §6.9 names "download course videos" specifically, and video is the one case where DECISIONS.md #13's existing signed-URL-read pattern doesn't already work offline (a PDF read still needs a live signed URL each time). Adding offline PDF caching "for symmetry" with nothing in the PRD asking for it, and no user story motivating it, is exactly the gold-plating CLAUDE.md warns against — left out on purpose, not an oversight.
**Why quiz grading stays server-side even when offline**: an offline quiz submission is queued as raw answers (`quiz_attempt`), never scored client-side — CLAUDE.md's "never trust a client-reported quiz score" rule doesn't get an offline exception. Shipping the correct-answer key to the device so it could grade itself offline would be a real integrity hole; the trainee sees "saved, pending sync" instead of an instant score, and the real score only exists once `syncManager` actually reaches the server.
**Known limitation, stated plainly**: downloads are not resumable — `Filesystem.downloadFile` re-downloads from the start if interrupted, unlike a true chunked/range-based resumable transfer. Real given PRD §7's low-bandwidth context, but building actual HTTP-range resume was judged more machinery than this round needed; noted as a real follow-up, not silently assumed solved.
**A second real gap found and fixed in the same round, not left as a surprise**: wiring the plugins into `apps/web/package.json` alone was not sufficient — `cap sync`'s native-plugin discovery scans the package.json of the directory it's run from (`apps/mobile`), not `apps/web`'s, so the three plugins were invisible to the native Android project until also added to `apps/mobile/package.json`. Confirmed via `cap sync`'s own output ("Found 3 Capacitor plugins for android") and by inspecting the generated `app/capacitor.build.gradle` directly, not just trusting a clean exit code.
**Status**: Active, and live-verified through an actual `./gradlew assembleDebug` build (not just `tsc`/`vite build`) — a real, installable `app-debug.apk` was produced with the offline module and all three native plugins correctly linked in. **Not yet done**: an actual on-device test of the full offline→reconnect→sync loop (needs a real phone or emulator, tracked the same way as F9's other device-dependent gaps); resumable downloads (see above); and the two remaining screens (`TraineeHome`, certificates) haven't been reviewed for their own offline needs beyond what PRD §6.9 explicitly names (lessons, quizzes, attendance).

### 24. Hosting: Render (Web Service for `apps/api`, Static Site for `apps/web`) — resolves ARCHITECTURE.md §15's `TBD`

**Decision**: `apps/api` deploys to Render as a Node **Web Service** (repo root as the build context — the pnpm workspace needs `packages/*` resolvable, so the service cannot be rooted at `apps/api` alone; build command runs `pnpm --filter api build`, start command `pnpm --filter api start`). `apps/web` deploys to Render as a **Static Site** (`pnpm --filter web build`, publish `apps/web/dist`), with `VITE_API_URL` set to the deployed API's Render URL as a **build-time** env var (Vite bakes `VITE_*` vars into the bundle at build time, not read at runtime — the same fact that caused the LAN-IP mobile bug this decision also permanently fixes, see below). `apps/mobile` gets no separate Render deployment — per Decision #22 it has no `src/` of its own and just wraps whatever `apps/web/dist` was built with, so pointing that build at the real HTTPS Render API URL instead of a LAN IP is what actually fixes the Android app for good.
**Why Render over the alternatives already on the table** (Cloudflare/Backblaze were evaluated for storage, not compute): free tier covers both a Node web service and a static site with no credit card required for the static site, native Git-push-to-deploy with no extra CI tooling needed (resolving the "no CI/CD pipeline exists yet" gap partially — deploys are still manual-trigger, not test-gated, so that half of the `TBD` stays open), and it needs zero Dockerfile or infra code for a plain Node + Vite monorepo — matching this project's "minimal, not gold-plated" rule better than standing up Kubernetes/ECS for a hackathon prototype.
**Two real, pre-existing risks found and fixed in this same round, not discovered by deploying blind**:
1. Root `package.json`'s `engines.node` was `">=20"`, but `apps/api` importing `@ncct/constants`/`@ncct/shared-types`/`@ncct/validation` (each `"main": "src/index.ts"`, i.e. shipped as raw TypeScript, never compiled — there is no separate build step for `packages/*`) only works at runtime because Node's *native* TypeScript type-stripping resolves those `.ts` files directly. That behavior is not available, at any Node 20.x version — it shipped experimentally in 22.6, and only became **default-on** starting at 22.18.0 (LTS) / 23.6.0. A Render service provisioned on Node 20 (a very plausible default for an unpinned `engines` field) would have built successfully (`tsc` doesn't care) and then **crashed immediately on boot** trying to `import` a `.ts` file it can't parse — a failure mode that only appears in production, never locally, since local dev always ran on Node 24.13.0. Fixed by raising `engines.node` to `>=22.18.0` and adding a root `.node-version` file (`22.18.0`) so Render's Node buildpack picks a compatible version without relying on the `engines` field being read correctly by every tool in the chain. Verified locally, not assumed: ran the actual production path (`pnpm --filter api build && node dist/index.js`, no `tsx`) and confirmed it boots and serves `/health` correctly — the workspace-package imports resolve via the same native stripping mechanism this decision now guarantees a compatible Node version for.
2. No `packageManager` field existed, so a fresh Render build environment had no guarantee of getting the same pnpm version (11.24.0) this project was built and tested against; a pnpm major-version drift can change lockfile resolution behavior. Fixed by adding `"packageManager": "pnpm@11.24.0"` so `corepack enable` (Render's documented way to get pnpm) activates the exact pinned version.
**Not changed**: CORS (`cors()` with no options, already wide-open) — no code change needed since there's no cookie-based session to leak; every authenticated request already carries an explicit bearer token, so an open CORS policy doesn't weaken anything the JWT check doesn't already guard. `PUBLIC_WEB_URL` (used only for the QR check-in link, Decision in F5's entry) is a plain env var update once the web Static Site's real URL is known — no code change.
**Status**: Active. Deployment steps and current URLs are operational detail, not architecture — not duplicated here; ask if they're not already in hand.
