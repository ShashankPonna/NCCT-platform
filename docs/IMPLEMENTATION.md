**Relevant files**: `supabase/migrations/20260901000001_init_schema.sql` (`profiles` table, `handle_new_user` trigger), `apps/api/src/middleware/auth.ts` (`requireAuth`, `requireRole`), `apps/api/src/supabaseClient.ts` (`supabaseAdmin`, `getSupabaseForUser`), `apps/api/src/routes/{profile,institutions,users}.ts` + matching `.test.ts` files (37 tests), `apps/api/src/app.ts`, `apps/web/src/{ProfileEditor,AdminUserManager}.tsx`.

All four once-"missing" pieces exist and were **live-verified 2026-09-03**: own-profile read/update (`GET /api/profile/details`, `PATCH /api/profile`) — and confirmed live that `role` is **not** self-editable through it, a trainee's attempt to patch themselves to `admin` leaving their role unchanged; institution CRUD (`POST/GET/PATCH/DELETE /api/institutions`, admin-gated — a trainee's create attempt correctly 403s); employer org profile fields (`org_name`/`org_sector`) settable via the same profile routes; and bulk trainee import (`POST /api/users/bulk-trainees`) genuinely reporting **per-row** partial success — verified by submitting one fresh address alongside one already-registered address in a single request and getting back `created` for the first and `skipped` (with the real reason) for the second, rather than the whole batch failing.
**Admin user directory & lifecycle (added 2026-09-03)** — the gap that "Auth & **User Management**" actually still had. Before this, an admin could _create_ accounts but never see them, and no route existed to change anyone's role: `handle_new_user` defaults every self-registered account to `trainee`, so a self-signed-up user was permanently stuck as a trainee with no path to trainer/admin/employer. `profile.ts` even carried a comment saying role changes "are an admin operation only" — describing an operation that did not exist. Three routes close it, all admin-gated:

- `GET /api/users` — the directory, with `?role=` and `?q=` filters. Emails live in `auth.users`, which PostgREST does not expose, so this is a deliberate two-source join in Node (`profiles` for the queryable half, one `listUsers()` page for addresses). `?q=` is applied in Node rather than Postgres precisely because it has to match the email, which is not a column on `profiles`. Stated limitation rather than hidden: the email page is fetched at the API's maximum size (1000) and beyond that a row comes back with `email: null` instead of the user silently vanishing from the directory — the profile half is never truncated.
- `PATCH /api/users/:id` — change another user's role and/or profile fields. `profiles.role` is the source of truth `requireAuth` reads on every request, so auth `user_metadata` (only a signup seed) is deliberately not written back.
- `DELETE /api/users/:id` — removes the auth user; `profiles` cascades via its existing `on delete cascade`, so there is no second delete and no window where a profile outlives its login.

**Two self-lockout guards, both enforced server-side and reflected in the UI**: an admin cannot change their _own_ role (they would instantly lose access to this very route, and a last remaining admin would lock the whole project out with no way back except the Supabase dashboard) and cannot delete their own account. Editing your own _non-role_ fields is still allowed — it is specifically the role that is refused. `AdminUserManager.tsx` greys out both controls for your own row rather than showing a button that always errors.

**Missing**: nothing from PRD §6.1. Note that row-level _schema_ validation is upfront and all-or-nothing by design: a malformed email fails `bulkImportTraineesSchema` and 400s the entire request, whereas partial-success applies to per-row _creation_ failures (duplicate address, etc.). That is a deliberate split, not a gap, but it's worth knowing which half of it a given failure lands in.
**Needs testing**: nothing untested — `requireRole` is now exercised extensively by F2's and F3's role-restricted routes (programmes/nominations/timetable/courses/modules/lessons), not just `requireAuth`.
**Known issues**: none identified.
**Dependencies**: none blocking.

2. 3. **The actual dominant cause, and a repo-wide bug rather than a mobile one**: `packages/api-client` keeps its base URL in module state, defaults it to `http://localhost:4000`, and exposes `setApiBaseUrl()` for each app to call at startup — but **nothing in the repo ever called it**. Verified in the built bundle itself (the minified output shows `n(He)` — the setter invoked with the LAN-IP constant — immediately before `createRoot`), and the rebuilt APK confirmed to contain that exact bundle.

- **2026-09-24 (1)**: **Kiosk reader and camera now advertise themselves via mDNS — DECISIONS.md #40 — per direct user request after being told (correctly) that both address fields were real per-network, per-reboot values with no way around retyping them.** Both `ESP32-CONTROLLER/arduino/kiosk_controller` and `ESP32-CAM/arduino/kiosk_capture_server` gained `#include <ESPmDNS.h>` (bundled with the ESP32 board package) and a `MDNS.begin(MDNS_HOSTNAME)` + `MDNS.addService("http", "tcp", 80)` call right after their existing WiFi-connect step — non-fatal, so a failed `MDNS.begin()` just falls back to each board's existing numeric-IP-on-Serial/OLED behavior, nothing regresses. The controller sketch re-issues `MDNS.begin()` on every reconnect, not just once at boot, since its `connectWiFi()` already runs again whenever `loop()` detects a WiFi drop and an mDNS advertisement needs re-announcing the same way. `apps/web/src/KioskTerminal.tsx`'s Reader/Camera fields gained two things in the same round: they now default to these mDNS hostnames (zero typing needed on a first-ever visit, on any network where mDNS resolves — true out of the box on macOS/Linux and in Chrome/Edge on Windows) and separately remember whatever the user actually typed via `localStorage` (covers the fallback-to-numeric-IP case on a network where mDNS is blocked). **Verified, not assumed**: the controller sketch's real logic harness (`ESP32-CONTROLLER/test/`) gained a matching `ESPmDNS.h` stub and was re-run against the actual modified sketch — 23/23 checks still pass, confirming the mDNS addition changed nothing about the state machine, timeouts, or wire protocol. `pnpm typecheck` (7/7), `pnpm --filter api test` (426/426), `pnpm lint`, `pnpm --filter web build` all clean. **Named limits, not glossed over**: the ESP32-CAM sketch has no equivalent logic harness (no harness existed for it before this change either — `esp_camera.h` is real ESP-IDF hardware surface, much harder to stub) so its mDNS addition was reviewed by hand against the identical, harness-proven controller pattern rather than independently compiled; and none of this has been flashed to real hardware or verified on an actual network yet — that's the user's next step, the same standing gap every piece of kiosk firmware has carried since DECISIONS.md #33.
- **2026-09-23 (14)**: **Rewrote the F5 kiosk controller firmware (`ESP32-CONTROLLER/arduino/kiosk_controller/kiosk_controller.ino`) from USB-serial to WiFi HTTP, per direct user request to run the DevKit+RC522+OLED reader unit fully wirelessly.** The user is moving that unit to a 3.7V LiPo → 5V boost converter into `VIN` — no USB cable to the kiosk PC at all — while the ESP32-CAM keeps its existing USB-powered setup.
