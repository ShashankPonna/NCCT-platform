**Working**: MCQ quiz builder — `assessments` CRUD (admin+trainer writes, any-authenticated reads) and `assessment_questions` CRUD, with a hard architectural split from every other content table: `assessment_questions` has no RLS read policy at all, ever, and every read goes through Express (`supabaseAdmin`), which strips `correct_option_id` for the trainee-facing `GET /assessments/:id/take` route but includes it for the admin/trainer authoring route (DECISIONS.md #15 — RLS can't filter columns, only rows). Server-side auto-grading: `POST /assessments/:id/attempts` reads the correct answers via `supabaseAdmin`, computes `score_percent`/`passed` itself, and ignores any client-supplied score/passed fields entirely — verified live by sending a request claiming a perfect passing score alongside all-wrong answers, which was silently ignored and graded 0%/failed. **Missing**: nothing from PRD §6.4's stated requirements. `AssessmentBuilder`/`QuizTaker` are as bare-bones as the rest of this repo's admin/student UI (no question editing/reordering/deletion UI, no attempt-history view beyond what the API already returns); no automated `apps/web` component tests (INFRA-5 still 🟡, same gap as every other web component so far).
**Needs testing**: nothing untested in what's built.
**Known issues**: none identified.
**Dependencies**: F3 (assessments hang off modules — satisfied); certificate revocation is an open PRD question (§14) — deliberately not in the schema, doesn't block issuance/verification. **Genuine open item, not silently resolved**: every passing assessment currently mints its own certificate (no "capstone assessment" concept exists in the schema or PRD), so a trainee could accumulate multiple certificates within one programme if it has multiple module quizzes — flagged in `DATABASE.md`'s Open Items rather than guessed at either way.
**❓ Needs clarification**: same as F3 — who can author assessments/questions (built as `admin`+`trainer`, PRD doesn't say). Also: whether one certificate per passing assessment is the intended model, or whether only a designated "final" assessment should certify (see Dependencies above).

**Acceptance criteria**: attendance is logged per trainee per session with a `method` of `qr` or `face`; a face-match below threshold falls back to QR rather than blocking the trainee (PRD §11 edge case); no face embedding is stored without `consent_given_at`.
**Status**: 🔵 IMPLEMENTED — NEEDS TESTING (both PRD §6.5 clauses built, unit-tested, and now fully live-verified end-to-end against the real API + real Supabase project with synthetic embeddings — see Working; the one remaining gap is a real camera producing a real embedding, which no environment available so far could exercise)

**Working**: QR check-in — `POST /api/attendance` (trainee, `method: "qr"`) inserts an own-row `attendance_records` row via `req.supabase` (409 on a duplicate check-in for the same session, 404 via a caught FK-violation for a nonexistent session); `GET /api/timetable/:sessionId/qr` (admin/trainer) generates a QR PNG (data URL, via the already-installed `qrcode` package) encoding a URL — `{PUBLIC_WEB_URL}/?checkin={sessionId}` — not just a raw session id, reusing the exact pattern `?verify=` already established for certificate verification (DECISIONS.md #6's NFC precedent: let the OS's native camera/QR app open a URL, no in-app scanner library needed); `apps/web`'s `App.tsx` checks for `?checkin=` the same way it already checks for `?verify=`, except after the login gate (a check-in genuinely needs an authenticated trainee, unlike verification) and auto-submits the QR check-in via `AttendanceCheckIn`'s `autoCheckInSessionId` prop. `GET /api/timetable/:sessionId/attendance` (admin/trainer) returns the session roster with denormalized trainee names. Face check-in — enrollment (`POST /api/face-embeddings`, trainee-only) requires an explicit `consent: true` in the same request that carries the embedding (the row's `consent_given_at` is stamped server-side at that moment — CLAUDE.md's DPDP Act 2023 rule); `GET /api/face-embeddings/status` reports whether a trainee has enrolled. Matching (`POST /api/attendance`, `method: "face"`) **always recomputes the match server-side** — the client only ever sends the raw embedding it extracted locally, never a match score or verdict (CLAUDE.md: never trust a client-reported face-match result, verified live by sending a spoofed `match_score: 0.01, matched: false` alongside a genuinely matching embedding and confirming the server ignored both fields and matched correctly anyway); cosine similarity (`cosineSimilarity`, unit-tested directly) is computed in Node against every embedding enrolled for that trainee (own-row only, 1:1 verification of the already-JWT-authenticated identity, not a 1:N "who is this" search — a documented judgment call, see DATABASE.md's Open Items) and the max score is compared against `FACE_MATCH_THRESHOLD` (0.6, an untuned starting point, same category as F4's `pass_threshold_percent`); a below-threshold match returns `200 { matched: false, match_score, fallbackToQr: true }` and writes **no** attendance record — the trainee isn't blocked, per PRD §11's explicit edge case — while an above-threshold match inserts the record with the server-computed `match_score`. Web: `FaceCapture.tsx` (webcam capture + `@vladmandic/human` browser-side extraction, lazy-loaded via dynamic `import()` so its ~1.5MB stays out of the main bundle, model files fetched from Human's own CDN at runtime rather than bundled — confirmed via `vite build`'s output that it code-splits into its own chunk); `FaceEnrollment.tsx` (consent checkbox gates rendering the capture UI at all, not just the submit button); `AttendanceCheckIn.tsx` (trainee: session-id input for QR, face capture + enrollment inline); `AttendanceManager.tsx` (admin/trainer: QR generation + roster table). 157 total API tests passing (28 new: 20 attendance incl. the cosine-similarity unit tests and the spoofing-is-ignored case, 8 face-embeddings incl. the missing-consent-is-rejected case). `pnpm --filter web build` succeeds. **Live-verified end-to-end** against the real API + real Supabase project (synthetic 512-number embeddings standing in for a real camera capture, since extraction itself is client-side and untestable from a script — see Missing): real enrollment with consent stamped server-side, consent-omitted enrollment rejected (400), a matching face check-in scored and recorded correctly, a spoofed client-reported score/verdict silently ignored in favor of the real server computation, a duplicate check-in on the same session rejected (409), a genuinely dissimilar embedding correctly fell back to QR (200, no record written) rather than blocking the trainee, an admin read the session roster with denormalized names while a trainee was correctly blocked from it (403), and QR generation returned a real data URL. **A real bug was found and fixed by this live run, not by the 157 mocked tests**: `face_embeddings.embedding` (a pgvector column) comes back from PostgREST as its Postgres _text_ representation (`"[0.1,-0.2,...]"`), not a parsed JSON array — the original code's `row.embedding as number[]` type assertion hid this at compile time, but at runtime `cosineSimilarity` was indexing into a string's characters, producing `NaN` throughout. This silently broke matching two ways at once: every real `match_score` was stored as `null` (`JSON.stringify(NaN)` → `null`), and `NaN < FACE_MATCH_THRESHOLD` is always `false`, so a genuinely dissimilar face would have incorrectly been treated as a match instead of falling back to QR — the opposite of PRD §11's required behavior. Fixed with a `parseEmbedding()` helper that `JSON.parse`s the string form (Postgres's vector text format is valid JSON array syntax); mocked unit tests never caught this because their table mocks hand back real JS arrays, never exercising PostgREST's actual serialization. Re-ran the full live check afterward and confirmed all cases pass with correct non-null `match_score` values and correct fallback behavior.
**Missing**: nothing from PRD §6.5's stated requirements at the API level. As with every other feature so far, the web UI is bare-bones (raw session-UUID text input, no session picker — F2 still has no browsing UI). Camera-dependent behavior (actual webcam capture, actual face detection against a real face) has **not** been exercised in a real browser in this environment — the live-verification round above proves the server-side matching/storage/consent/fallback logic is correct against real Postgres, using a fabricated embedding vector in place of a real camera capture; it does not prove `@vladmandic/human` actually produces a good-quality embedding from a real face in a real browser. That needs a manual check with camera access before this is trusted beyond "implemented."
**Needs testing**: only the live webcam frame source (`getUserMedia` → `<video>` → canvas) remains unconfirmed. Everything downstream of that frame — Human's detection, the 1024-d descriptor, enrollment, server-side matching, threshold behavior — is now verified with **real face descriptors** (see below). This is ordinary browser-API glue and much lower risk than it was, but it hasn't been exercised against an actual camera.
**Known issues**: none currently. Two real bugs were found and fixed in this feature's verification rounds — the pgvector string-vs-array deserialization bug, and the 512-vs-1024 descriptor dimension bug (below) — neither left open.

**Real-face verification (the round that closed the extraction gap)**: `@vladmandic/human`'s browser build was driven headlessly (Playwright + Chromium, WebGL/SwiftShader) using **the exact config `FaceCapture.tsx` uses**, against real face photos, then the resulting descriptors were pushed through the live API. This uncovered a **schema-level bug that had made the whole face path unusable in practice**: Human's faceres descriptors are **1024-dimensional**, not 512. The initial migration's comment claimed "512-d to match the Human / InsightFace buffalo_l output size", which conflated two different models — `buffalo_l` is genuinely 512-d, Human is not — and nothing had ever measured it. Consequences, all fixed together in migration `20260901000011`: the `face_embeddings.embedding` column could never have stored a real descriptor; `enrollFaceEmbeddingSchema`/`attendanceCheckInSchema` rejected every real capture as a 400; and `FaceCapture.tsx` reported **"No face detected" for a face it had successfully detected** (score 1.0) purely because its length check failed — which is precisely the symptom the user reported earlier and which the console diagnostic had not been enough to explain. That misleading message is also fixed: "no face found" and "face found but no usable descriptor" are now distinct errors with distinct console diagnostics. **Why the earlier live round missed it**: it fed synthetic 512-length vectors end-to-end, so every layer agreed with every other layer and all of them were wrong together — the specific hazard of verifying a pipeline with fabricated data. After the fix, verified with real descriptors through the running API: enrolling a real 1024-d descriptor succeeds; a **second capture of the same face** matches at **0.987** and records attendance; a **different person's face** scores **0.302** and correctly falls back to QR. That also sanity-checks `FACE_MATCH_THRESHOLD` (0.6) for the first time against real data rather than assumption — it sits cleanly between the two, with same-face separately measured at 0.85–0.94 across rescaled captures.
**Dependencies**: F1 (consent capture needs an authenticated trainee — satisfied); F2 (sessions come from `timetable_sessions` — satisfied). Face-rec library: `@vladmandic/human` is now installed, but **only in `apps/web`**, not `apps/api` — see the ❓ note below and DECISIONS.md #16 for why.
**❓ Needs clarification / significant judgment call, flagged rather than silently assumed**: DECISIONS.md #5 originally described face embedding extraction running server-side in Express via `@vladmandic/human` + `tfjs-node`. Before writing any F5 code this round, that path was actually attempted (not just assumed to work) on this Windows dev machine: `@tensorflow/tfjs-node`'s native bindings failed to install outright (no prebuilt binary for this Node/ABI combination, and the native-compile fallback needs Visual Studio's C++ build tools, which aren't installed); the alternative WASM Node build installs and loads cleanly but a real test (a photo with multiple clearly visible faces) returned **zero** face detections while the same pipeline's body detector correctly found a person in the same frame — a reproducible wasm-backend-specific failure in the face detector, confirmed not a config mistake by also trying a much lower confidence threshold. Given this, extraction was moved to run client-side in `apps/web` instead (`@vladmandic/human`'s primary, best-supported environment — browser WebGL), with Express's role narrowed to storage + server-side-recomputed matching. This is a real architectural reversal, documented in DECISIONS.md #16 rather than silently diverged into, and is exactly the kind of thing worth surfacing rather than assuming either way: if a future environment _can_ install `tfjs-node` cleanly, moving extraction back server-side is possible without changing the `face_embeddings` table shape, but there's no code reason to do so given the browser path works and is arguably better for data minimization (raw camera frames never leave the trainee's device).
